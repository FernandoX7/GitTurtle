# Persistence and GitHub boundary audit — 2026-09-10

This bounded audit contributes to the [security and quality milestone](security-quality-milestone.md). The coordinator owns integration, final gates, native interaction, packaging and installation. All mutation fixtures below use temporary application data, disposable local subprocesses, a dummy authorization token, Unix sockets or a refusing loopback proxy. No saved account token or real GitHub account was accessed.

## Scope and trust model

The inspected paths were application preferences/commit drafts, recovery drafts, named profile storage, repository sessions, activity history, GitHub drafts/attempts, GitHub service and transport, and the native collaboration dispatch boundary. Relevant contracts were [writes and persistence](../crates/app/docs/writes-and-persistence.md), [authentication](authentication.md), and [GitHub collaboration](github-collaboration.md).

Repository-derived identities and provider text enter owned models, native plain-text rendering and bounded JSON stores. UI edits enter the coalescing saver; accepted persistence work runs on the separate serialized preferences executor. The atomic writer creates a private temporary file, syncs it and renames on the same filesystem. Outbound reviews use the operation executor, captured account/repository/head/base identities and an independently persisted pending attempt before the one explicit POST. Credentials travel from the platform secure store through the API subprocess environment, independently of draft JSON.

The app-data directory belongs to the current operating-system user. Corrupt files, unexpected file types and concurrently changing files should not block startup, overwhelm reads or destroy recoverable data. These checks are not a sandbox against another process with the same user's filesystem/Keychain permissions. The supported provider is GitHub.com; a separate CLI routing preference must not silently redirect the app's separately stored token while the app displays that provider.

## Finite findings and corrections

| Finding | Trigger and impact | Correction and evidence |
| --- | --- | --- |
| PERSIST-1 — bounded file reads, P2 | GitHub loaders checked pathname metadata and then used unbounded `fs::read`; replacement/growth could bypass the bound. Other store loaders opened FIFOs and symlinks directly, potentially blocking startup or the only persistence executor. | `preferences::read_store` opens one descriptor, rejects nonregular files and checks both descriptor length and actual bytes consumed. Unix opens add `O_NOFOLLOW` and `O_NONBLOCK`. Preferences/commit, recovery, profiles, sessions, activity and GitHub stores share this boundary. Tests cover final-component and dangling symlinks, FIFO refusal without a writer, preservation on refused preferences saves, exact-limit files, directories and content growth after observing metadata. |
| PERSIST-2 — encoded attempt limit, P2 | Per-string 4 KiB and 128-entry limits did not bound encoded JSON. A legitimate 128th long entry, or JSON escaping, could write a file over the loader's 1 MiB limit, making later attempt recording refuse its own output. | `github::drafts::record_attempt_at` checks serialized bytes before replacement. Overflow retains the prior readable file; failure to record a pending attempt still prevents dispatch. The adversarial fixture exercises ordinary-byte and escaped-control overflow and a subsequent successful outcome update/reopen. |
| PERSIST-3 — coalesced batch atomicity, P2 | A batch saved each identity separately. A later limit error could leave earlier identities persisted despite the batch failure, and N pending drafts could reread/serialize/publish the complete store N times. | `save_batch_at` merges the batch once and validates before a single atomic publication. A 127-entry fixture updates an old draft, adds one entry, then crosses the entry limit; failure preserves the exact original bytes. A valid batch subsequently restores both updated and new text. This removes write amplification by construction; no latency or allocation improvement is claimed without release measurement. |
| PERSIST-4 — corrupt session preservation, P2 | Session startup fell back to defaults for malformed or unsupported JSON. A later navigation/quit save could overwrite the original tabs/library/bookmarks with that default session. | `Session::save_at` rereads and validates the current disk store before publication, permitting a missing file and refusing unreadable/corrupt/unsupported data. The startup fallback remains usable. Tests preserve truncated and unsupported-version bytes and prove normal first-save/update/reopen still work. |
| GH-1 — API credential routing, P1 | Installed GitHub CLI 2.100.0 accepts `api_host` even with `--hostname github.com`; `http_unix_socket` can route the request and authorization to a local socket. Inherited CLI configuration therefore controlled the route for GitTurtle's separate Keychain token. | API requests use an absolute `https://api.github.com/` URL plus an empty private `GH_CONFIG_DIR` whose lifetime covers the subprocess. The explicit `gh auth token` handoff retains configured CLI account lookup. The opt-in installed-CLI fixture uses a dummy token and disposable overrides, then observes normal HTTPS CONNECT at a refusing loopback proxy after isolation. |

## Transport and ownership audit

`Repository::parse` restricts provider/owner/name syntax; branch components are percent encoded, local template reads require captured regular Git blobs, and pagination links only signal another explicit page. The app does not follow provider pagination URLs. `Client::execute` rechecks the captured head/base and open state, includes the reviewed commit in a review and does not automatically replay an accepted request. The native confirmation captures the account; submission compares it again with the secure-store transport, and busy state/consumed confirmation prevent an ordinary duplicate click. Accepted operation execution survives losing the UI receiver; persistent pending/outcome messages retain the need for explicit verification after uncertain failure.

The installed CLI reported `gh version 2.100.0 (2026-09-03)`. Its versioned [API request construction](https://github.com/cli/cli/blob/v2.100.0/pkg/cmd/api/http.go) and [configuration lookup](https://github.com/cli/cli/blob/v2.100.0/internal/config/config.go) establish that relative API routes honor `api_host`. Its [authorization transport](https://github.com/cli/cli/blob/v2.100.0/api/http_client.go) maps the configured API host back to the account token and avoids adding authorization on a hostname-changing redirect. The dependency's [HTTP transport](https://github.com/cli/go-gh/blob/v2.16.0/pkg/api/http_client.go) implements the configured Unix socket route and delegates redirects to Go. This source review motivated GH-1; the fixture uses no external service.

`github::transport::run` makes stdin/stdout/stderr nonblocking, performs I/O and process polling in one bounded loop, closes stdin once the request is sent and waits for output EOF as well as child exit. Cancellation/deadline errors kill the process group and reap the direct child. The response budget is 8 MiB plus 64 KiB framing; diagnostic bytes are discarded and limited to 64 KiB. The API deadline is 90 seconds; CLI token handoff uses 30 seconds and 16 KiB output. The new pipe-lifetime test has a parent exit while its child keeps stdout open and requires the deadline to end the operation. Existing tests cover cancellation, EOF and output overflow.

The batch change reduces complete-store publications from one per draft to one per accepted batch. Session recovery protection adds a bounded read/parse before saving. Private API configuration adds a temporary directory per explicit API command. These are explicit correctness/ownership tradeoffs, with no release latency, CPU or allocation claim from the targeted test timings.

The supported Unix open protects the final filename, not hostile replacement of its parent hierarchy. The non-Unix fallback does not establish Unix-equivalent race resistance. Multi-process transactions remain outside the single app-instance persistence executor contract (profile definitions already have their own storage lock). A slow regular file on an unresponsive filesystem can still delay I/O; nonblocking mode prevents FIFO-open waits, not all kernel/filesystem stalls. Atomic file publication uses the existing best-effort directory sync and cannot guarantee survival of every hardware failure or forced termination beyond the documented shutdown grace.

The CLI executable, OS trust store, configured HTTPS proxy and provider's authenticated redirects remain trusted dependencies. GitTurtle pins initial API routing but does not receive the final redirected URL or install its own redirect policy through `gh api`. GitHub branch-name creation remains subject to the documented check-to-acceptance race, and provider permission/account changes remain possible. No live GitHub action, real Keychain unlock, Linux desktop interaction or hosted CI success is implied by these fixtures. No credentials were persisted in the fixture configuration or evidence.
