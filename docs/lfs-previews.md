# Explicit LFS preview downloads

Missing LFS image and model previews expose **Download Before…** / **Download After…**. Text pointers expose the same actions. Models resolve each local side independently: a missing or corrupt object retains its exact copyable pointer and error while the available opposite model remains interactive. Failed model sides remain retryable and are excluded from immutable caching; only a missing object offers a download. An image's or model's side says what is wrong in the same words as a text side, and those words reach the rewritten-series preview and Stashes as they do Compare. The native form identifies the selected file, SHA-256 object ID, known size, configured remote, and redacted effective LFS endpoint before confirmation. Source preparation stays passive in the repository: because `git lfs env` creates local storage directories, its configuration query uses private temporary storage which is removed afterward.

It executes `git lfs fetch --all <remote> <pointer-blob-oid>` for one exact pointer blob. A blob has no reachable sibling files or history, so the scan is scoped to that object; automatic recent-ref fetching and transfer retries are disabled for this command. The [Git LFS fetch implementation](https://github.com/git-lfs/git-lfs/blob/main/commands/command_fetch.go) passes explicitly supplied object IDs to the bounded selected-ref scan rather than the all-references path.

For a changed working pointer not stored in Git, a private temporary object directory holds the single pointer blob for the transfer. That Git object does not enter the repository's object store. No checkout, smudge, stage, prune, push, or working-file rewrite occurs. Configured filters are not used to manufacture a preview.

The plan revalidates repository directories, pointer bytes, unused local-object state, effective configuration, and LFS source before download. The downloaded object must pass the existing descriptor-relative, no-follow local-storage checks, expected size, and SHA-256 verification before decoding. The download cap is 32 MiB; text, image decoder, and decoded-memory budgets still apply. Effective global/system, repository, and private-worktree `lfs.storage` settings are now read consistently for lookup and transfer. Reference-object stores are not independently searched by GitTurtle.

Available LFS text objects are displayed as content, each side on its own: a side whose object is in the local store shows it, a side whose object is missing stays its pointer, says so and offers its download, and a side whose object is over the 32 MiB preview limit, fails verification, or lies in a store that cannot be read stays its pointer and says which, offering no download, which could not help. Those are three states. Over the limit is judged from the pointer alone, without reading the store. A corrupt object is what the read found at the object's own path: a size or SHA-256 digest other than the pointer's, or something that is not a regular file. A store that cannot be read says nothing about the object: a symbolic link in the store's place, in one of its directories or in the object's place, which the read never follows, or a permission or I/O error from the system, says "the local Git LFS store could not be read" rather than call every pointer in it corrupt. A corrupt object says only that its local copy is damaged: no repair is named, because a step this application cannot verify could dead-end, as with a healthy object whose pointer declares the wrong size, which reads as corrupt, stays where it is and never offers a download. One side's object never takes the other side's preview: reading a pointer's object is a passive look at the local store, and only a failure of the repository itself still fails the preview. Where a resolved side has no text to set beside the other's pointer, as with binary content, or nothing resolves, the comparison stays the two pointers; a local object that cannot be shown as text, being binary or too large to set as text, is still never called missing or offered for download. The underlying Git pointer remains each file's staging target. Partial staging is therefore disabled for resolved LFS text, with a visible explanation and whole-file staging available. Missing immutable LFS image and text results are not cached permanently: a preview in which either side's object is missing from the local store is not cached, whatever the other side holds, a notice that shows neither side beside binary content included, so an object that arrives is seen on the next read. A successful download reloads the captured selected preview only if its repository, file, mode, and request generation still match; Quick Open's working scope reloads raw working bytes without leaving its retained inspection.

Preparation requires Git LFS 3.8.1 or newer and asks `git lfs version` before any other Git LFS command reads the repository. Earlier releases let a repository's `.lfsconfig` or submodule configuration select a command that runs while fetching ([CVE-2026-105803](https://github.com/git-lfs/git-lfs/security/advisories/GHSA-x72p-hmqp-46hw), [CVE-2026-105802](https://github.com/git-lfs/git-lfs/security/advisories/GHSA-xrgv-7vx6-5vx6)); upgrading is the only fix, so an older or unrecognized version is refused with an explicit update instruction. This covers only GitTurtle's own download: clone, checkout, pull and other explicit operations keep the user's configured Git LFS filters, so an outdated installation remains exposed through them as it would be in a terminal.

Missing tooling, absent configuration/remotes, unavailable or corrupt server objects, moved pointers, and changed configuration produce explicit errors. A cancellation or lost result can leave verified local content or temporary Git LFS transfer state; the application does not retry automatically. Hosted-provider checks require a separately authorized destination and are distinct from local evidence.

## Local evidence

`cargo test --locked -p gitturtle-core --test lfs_download` passed four disposable local-remote fixtures with installed Git LFS 3.8.0. They verify passive preparation, exactly one downloaded object despite unrelated/recent pointers, private temporary storage for raw working pointers, unchanged HEAD/index/working bytes, stale configuration/pointer refusal, corrupt source refusal, and cancellation during an active custom-adapter transfer. The cancellation test observes the transfer request before cancelling and verifies prompt process termination.

On October 25, 2026 (Linux AArch64, Git 2.55.0, empty system and global Git configuration) the same fixture ran against the official linux-arm64 Git LFS 3.8.1 and 3.8.0 builds, each checked against its release digest. With 3.8.1, the four transfer fixtures passed, including the custom adapter configured in local repository configuration. With 3.8.0, `git_lfs_before_3_8_1_is_refused_before_any_transfer` passed and the transfer fixtures reported that they were not run; without Git LFS, all five report that. The module unit test covers the accepted, vulnerable and unrecognized version strings.

The worker regression `lfs_text_preview_retries_missing_pointer_and_displays_verified_content` checks the transition from an uncached missing pointer to verified displayed text with no partial staging actions. The existing image counterpart checks local-miss retries and verified image caching. Native review, authentication interaction, and installed-build evidence are recorded in the combined milestone verification record.
