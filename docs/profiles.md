# Named Git profiles

The header profile control opens a native keyboard menu. Choose a saved profile to review its application, or open **Manage profiles** to create, edit and delete definitions. Profiles contain a label, Git author name/email and optionally a snapshot of the current public signing reference, signing format, and enabled commit/tag signing requirements. They contain no credential, password, token or private-key bytes. Hosted-provider authentication continues through Git's configured helpers and agents.

Saving a definition changes app preferences only. **Apply profile** reviews the displayed canonical worktree and exact configuration path before submitting one serialized Git operation. Reopening a project never reapplies a saved assignment. The header displays the saved profile label and **differs** when the effective Git author/signing settings no longer match it. Changing a saved definition also exposes that mismatch until a separate application.

Application changes repository configuration shared by linked worktrees, or the current worktree's private `config.worktree` when `extensions.worktreeConfig` is already enabled. The review explicitly discloses the shared scope. GitTurtle does not enable that extension or change global configuration. Private overrides in other worktrees remain effective. Inherited include files and unrelated keys, configured programs, hooks and credentials remain intact; explicit profile values are placed after includes so the chosen identity takes precedence in its reviewed scope. Environment identity overrides can still differ from configuration; the effective author remains visible.

The core captures the original effective identity, scope and bounded configuration bytes, revalidates them and reserves Git's configuration lock. All keys are prepared before atomic publication. Stale plans and existing locks refuse application without partial identity changes. A profile never writes a false signing requirement: omitted signing settings inherit the repository, and saved enabled requirements can only enable signing. Active merge/rebase/cherry-pick/revert state must be finished or aborted before changing identity. Unavailable signing keys fail through normal Git handling; no unsigned fallback is attempted. Signed annotated tags receive the required newline before their signature marker even when the typed annotation has no final newline.

Profiles retain `tag.gpgSign` and the narrower `tag.forceSignAnnotated` requirement separately. Annotated-only signing leaves lightweight tags available and forces signing for the annotated workflow, including where Git's explicit `--annotate` option would otherwise override that configuration. The [Git tag documentation](https://git-scm.com/docs/git-tag.html) describes those option/configuration precedence rules. Editing a profile can explicitly capture the current repository's signing settings again.

Definitions and worktree assignments live in `profiles.json` alongside application preferences, independently of themes and drafts. The existing preference executor serializes atomic read/merge/write saves. A persistent advisory-lock file coordinates other application instances and the OS releases its lock after process termination. Version, size and field checks preserve invalid or newer stores rather than replacing them. Storage supports up to 64 named profiles, 512 assignments and 512 KiB; names are unique without case distinctions. Unix worktree names retain their original bytes. Editing and deletion compare the expected saved definition to avoid overwriting a concurrent edit. Save failures retain editor text, expose an error and offer an explicit retry. An assignment save failure after successful Git configuration does not undo or repeat that Git operation.

Deleting a definition removes only its saved assignments. Existing repository identity, repositories, signing keys, drafts and other saved work remain in place.

## Behavioral validation

`cargo test --locked -p gitturtle-core --test profiles` exercises real commit and annotated-tag author/committer identity for Personal and Work, shared versus existing private worktree configuration, stale config and held-lock refusal, include preservation and explicit identity precedence, and two generated SSH signing keys. Both commits and tags are cryptographically verified. Removing the selected key then refuses commit and tag creation while preserving HEAD, index and configured signing. The test also checks the configured commit hook and signed annotation without a final newline.

`cargo test --locked -p gitturtle profiles::` exercises definition/assignment restart persistence, retained other profiles, edited-profile stale-delete refusal, invalid/newer storage preservation, read-only missing-store loading and byte-safe worktree assignments. Native verification belongs in the current milestone record: header padding/hover/focus, menu Up/Down/Return/Escape, modal cancellation and retained edits, create/edit/delete, explicit application review, mismatch after external edits, and installed-app restart persistence. These core/store fixtures do not establish native interaction or hosted/hardware signing coverage.

The [current first-party GitKraken profiles guide](https://support.gitkraken.com/gitkraken-desktop/profiles/) informed the visible header picker and manage/create/edit workflow. GitTurtle retains its own artwork, appearance preferences and repository-scoped explicit-application policy.
