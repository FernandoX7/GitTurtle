# Explicit Git authentication

Clone, Fetch, fast-forward Pull, branch Push and named-tag Push use Git's existing credential helpers and SSH configuration. They run only after a user action. GitTurtle keeps the configured identity, hooks, filters, signing and host verification, and never changes global Git or SSH configuration to make an operation succeed.

Git credential helpers remain first in Git's credential flow. macOS `osxkeychain`, Git Credential Manager, custom helpers, `SSH_AUTH_SOCK`, SSH identity selection, and existing `GIT_ASKPASS`, `core.askPass` and `SSH_ASKPASS` programs retain their normal roles. An explicitly configured helper may open its own sign-in UI. This follows [Git's credential lookup order](https://git-scm.com/docs/gitcredentials) and [Git Credential Manager's interactivity setting](https://github.com/git-ecosystem/git-credential-manager/blob/main/docs/environment.md#gcm_interactive). A caller's explicit disabled-interaction setting is preserved.

When Git needs a response and no askpass program is configured, GitTurtle opens a native dialog. Username fields show their text; tokens/passwords and key passphrases are masked. A new SSH host is a distinct verification prompt: the user must verify its fingerprint before accepting. The application does not weaken SSH verification or replace a changed host key. Git signing continues through the configured GPG/SSH program, agent or pinentry; failure never causes an unsigned retry.

The response crosses an operation-specific Unix socket inside an atomically created mode-0700 directory, then reaches the requesting Git/SSH process through its normal askpass stdout. Socket requests and responses are length-bounded; at most 16 prompts are accepted per operation. The socket is removed when the operation finishes. This is local same-account IPC, not a security boundary against other programs already running as the same user. Credentials remain transient in app memory. GitTurtle stores no credential in preferences or recents; configured credential helpers may save accepted credentials according to their own existing policy.

HTTP clone URLs with embedded userinfo, queries or fragments are refused before creating a destination. Existing remote addresses are displayed with credentials and query values hidden. Diagnostics redact URL userinfo/query data, authorization headers, credential assignments and exact secret responses submitted through GitTurtle. Inherited Git/GCM tracing is disabled for these subprocesses. Arbitrary configured hook/helper code still runs with the user's permissions; its own external side effects and private logs are outside the app's control.

Cancel is available beside the busy operation. It stops Git and its process group, including a waiting askpass or ordinary pipe-holding child. Numeric transfer phases are displayed when Git reports them. Local commands retain a 90-second deadline and network commands 180 seconds per command; custom helpers and signing programs share those bounds. A cancelled, timed-out or failed operation can already have changed local or remote state. The app refreshes local state afterward and explains uncertainty. It never replays the write. Checking a remote after an uncertain Push requires a separate explicit network action; local Refresh cannot prove the remote outcome. On macOS and Linux, nonblocking pipe I/O lets the app stop and join all of its reader/writer threads even when a configured helper creates a separate session while retaining pipe descriptors. An independently daemonized helper or agent owns its own lifetime after leaving Git’s process group; cancellation does not claim that such an external process was stopped.

An expired HTTP credential receives Git's normal helper rejection/erase flow and actionable guidance. The user can update the affected account in the configured helper, then retry deliberately. SSH guidance covers the configured identity/agent and macOS SSH Keychain options. A missing helper or signing program points to the applicable Git setting instead of silently replacing it.

## Verification and limits

`cargo test --locked -p gitturtle-core --test authentication` uses a loopback HTTP server and disposable helper to verify authenticated Fetch/Pull, helper approval and expired-credential rejection, ref outcomes, preserved local bytes, no replay, and secret-bearing clone refusal. Core authentication unit tests exercise the real Unix-socket exchange, masked-secret classification, cancellation while waiting for credentials, stale answers, directory cleanup, configured askpass precedence, diagnostic/progress secret redaction (including Unicode), cancellation after a fixture command has partially applied, and cancellation with detached helpers retaining output or input pipes. Existing workflow tests cover local clone/push, SSH host/key diagnostics and signing failure without an unsigned commit.

These fixtures do not establish live GitHub/GitLab/Bitbucket account sign-in, actual Keychain unlock, hardware-backed keys, signing-device/pinentry behavior or Linux desktop prompts. Those need the appropriate available environment and, for hosted accounts, an explicitly authorized destination. Native fixture interaction evidence belongs in [the prior milestone record](macos-milestone.md) and [the current review verification](review-native-verification.md).

`cargo test --locked -p gitturtle-core --test signing` verifies real configured SSH signatures for commits and annotated tags using a generated Ed25519 key held only by an isolated agent: the private key file is deleted before signing. It verifies both signatures, the commit hook, and failure without unsigned fallback after the agent stops, preserving HEAD, index entries and working bytes. Two optional tests, run with `-- --include-ignored`, additionally verify configured OpenPGP signing in a disposable keyring and an actual agent-authenticated Fetch through a loopback SSH server. The latter pins its generated host key, rejects an unknown host, and checks remote-tracking refs and unrelated local bytes. Optional tests require GnuPG or a usable local `sshd`; they are not part of the ordinary hosted test command.

All three signing fixtures passed locally on 2026-09-08 on macOS 26.6.2 arm64 with Apple Git 2.50.1, OpenSSH 10.3p1 and GnuPG 2.5.22. The authentication integration tests (3) and authentication unit tests (6) also passed. The installed Apple Git `osxkeychain` helper and a user login Keychain were present; no stored item was accessed and no Keychain unlock was exercised. These results establish disposable local transport and cryptographic signing, with the hosted-account, hardware and native prompt limitations above still open.

## Automated quality gates

The [September 9 milestone environment record](benchmarks/2026-09-09-milestone-environment.md) adds current isolated SSH-agent/OpenPGP signing, loopback HTTP/SSH/helper, cancellation and Keychain-presence checks, with exact commands and source-input identities. Its Linux container results are recorded separately from native and hosted-provider evidence.

[The quality workflow](../.github/workflows/quality.yml) runs locked workspace tests, formatting, Clippy and release compilation on macOS 15 and Ubuntu 24.04. It uses Rust 1.98.0 (the workspace toolchain), a pinned checkout action with read-only permissions and no persisted checkout credential, isolated runner Git configuration, and Linux native build libraries. It contains no distribution, upload, signing or publication step. Its Linux dependencies follow the [upstream native build setup](https://github.com/longbridge/gpui-component/blob/main/script/install-linux.sh), excluding optional webview libraries that are absent from this application.

The workflow configuration and local commands can be verified here. A hosted green run and actual Linux compilation/interactions must be reported separately; authoring the workflow does not establish that they passed.
