# Repository tabs and local workspaces

GitTurtle opens up to eight repository tabs. A tab identifies a canonical working-tree root: opening the same folder, a nested folder, or a symlink alias selects its existing tab after passive discovery. Linked worktrees remain separate tabs even when they share objects and references. Each tab shows its repository name, with its full path in the tooltip and accessible name; the active tab and a running Git operation have explicit state. The header's working branch and worktree context remain separate from the selected history scope.

Use **+**, Command-O, or Command-T to open a tab; click a tab, use Control-Tab/Control-Shift-Tab, or Command-Option-1 through 8 to select it. The Workspaces menu lists every open tab and offers Move current tab left/right, so overflow and reordering remain keyboard accessible. Command-W closes its tab; Command-Shift-W closes the window. The command palette exposes switching, closing, reordering, pinning, and local workspaces. Open dialogs contain their interaction: tab switching does not activate underneath them.

**Workspaces → Pin current repository** adds a persistent library entry. **Manage saved workspaces…** creates named local groups, assigns the current repository, opens a group's tabs, removes groups, and removes library entries. Removing a group keeps its repositories in the library; removing a library entry or closing a tab does not delete folders or commit drafts. The library holds 128 repositories and 16 groups with names up to 64 UTF-8 bytes. A repository belongs to at most one named group. Opening a group checks the eight-tab limit before adding it and reads only the selected repository; it never fetches, checks out, or performs a bulk Git operation.

The interaction research used GitKraken's first-party [interface](https://help.gitkraken.com/gitkraken-desktop/interface/) and [workspaces](https://help.gitkraken.com/gitkraken-desktop/workspaces/) documentation. GitTurtle's groups are local application state, without a shared or cloud workspace service.

## Retained views and resource ownership

A warm tab retains its history scope, captured history/search state, selected immutable commit, merge parent, query, navigation expansion and position, file filter/selection, scroll handles, resizable panels, working-file selection, and nested File History, revision comparison, and Blame return contexts. Existing editor entities retain their source selection and scroll. Commit drafts continue to use canonical worktree keys in the serialized preference store. Completed writes clear only the exact submitted draft; later edits remain saved.

There is one foreground repository worker and one active local watcher. Switching invalidates read generations, cancels pending status/inspection work, closes the ordinary history process on the worker, and drops the old watcher. Retained GIF comparisons pause at their current frame. PDF requests, model rendering, and Markdown local-link reads are canceled for both the displayed content and nested return contexts. Returning attaches the watcher and requests a passive rescan; it does not silently replay a write or restart a paused search. Ordinary deep browsing restarts its pinned traversal and discards bounded pages when the previous process is no longer available.

The application permits at most eight tab identities and a conservative 512 MiB allowance for retained tab data. Accounting includes commit/graph metadata, retained search and nested inspection data, captured content, and a fourfold content reservation for editors and native image surfaces. The active tab participates in the decision to retain another view. If switching would exceed the allowance, GitTurtle keeps the current view and asks the user to close a tab; it does not silently evict an inspection. Closing a tab releases its retained entities. This is an admission budget, not a claim that total application RSS is capped: shared toolkit, worker caches, allocator, Git topology, and GPU resources have separate costs. Native lifetime evidence is recorded with the exercised build in the milestone record.

## Restart and unavailable repositories

**Settings → Restore repository tabs on startup** selects whether to reopen the saved active tab or start at Projects. An explicit command-line repository takes precedence. Session reads are limited to 16 MiB in `repository-session.json`, beside `preferences.json`, and writes run through the same serialized application-data writer. Quit waits for its snapshot save. Only the selected repository is discovered on startup; other saved tab identities remain cold until selected. No credentials or GitHub tokens are stored in this session.

Restart restores the selected scope, pinned history offset, literal search query, selected commit identity/merge parent, history position, pane widths, and selected file. When the top view is an immutable comparison, its exact blob IDs, filenames, modes, and revision origins are restored. PDF sides preserve page and zoom, model sides preserve camera/link/wireframe choices, and Markdown preserves rendered/source mode and independent block positions. A selected commit outside the first loaded window is retained separately without adding an unbounded history prefix. A restored search resumes from its pinned scope in bounded pages; a restored comparison may leave that search paused until **Continue**.

Cold restoration applies the saved viewport without letting loading geometry replace it. Manual scrolling, including while the selected commit's file read is pending, stays intact; initialization must not replace it with row zero or force the selection into view.

Restart does not serialize decoded pixels, editor entities, every loaded search result, mutable working-file snapshots, or the full nested inspection stack. These survive warm tab switching; after process restart the addressable top comparison and repository history are restored. Objects that have been pruned or unavailable scopes produce the ordinary read error instead of substituting new revision contents. A cold comparison initially lists its captured file; selecting its commit loads the full changed-file list. The session is bounded to eight tabs; older saved files with more entries are normalized to that limit.

Moving or removing a repository does not cause automatic filesystem searches or retarget a tab. The original tab remains available with an actionable opening error. Explicitly open its new location, or reconnect its volume/access and retry the existing tab. Drafts at the old canonical path remain saved; GitTurtle does not automatically assign them to a different worktree. Closing an unavailable tab retains its pinned/library entry and recoverable draft.

## Accepted operations

An accepted operation captures a `GitRepository` and canonical worktree path before entering the serialized write executor. Tab switching changes only the viewed repository. Activity records, successful outcomes, errors, recovery form feedback, and draft completion route to that captured path. The global operation indicator names the running repository; completion in an inactive tab directs the user there for details. Closing the operation's own tab is refused with its operation/path and a Wait or Cancel recovery instruction. Other tabs remain switchable and closable. A completed Clone/Create does not replace a repository the user switched to while it ran.

## Evidence

`cargo test --locked -p gitturtle repository_tabs::tests` exercises active identity through reorder/persistence, normalization of duplicate/invalid entries, cold/unavailable restoration without discovery, library persistence after closing tabs, count and byte limits, exact captured selections/comparison identities, and non-UTF-8 paths. History traversal tests and [release benchmarks](benchmarks/2026-09-10-history-pagination.md) cover pinned continuation, graph/order semantics, cancellation, and bounded windows. Unit tests do not establish native focus, VoiceOver, or GPU cleanup; those require the coordinator's current native milestone evidence.
