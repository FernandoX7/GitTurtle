# Linux reduced motion and contrast from the settings portal (2026-10-28)

Research for the owner decision of 2026-10-28 in item 9 of phase 3 of [full Omarchy support](omarchy-full-support.md#phases) ("The desktop's reduced-motion and contrast preferences read automatically (the XDG settings portal), as macOS reads its accessibility preferences"), using the [research template](research-template.md). Code references are at `c219a6f`; nothing was built or changed, and no desktop setting was changed.

## Decision and scope

- **Question:** how GitTurtle reads the desktop's reduced-motion and contrast preferences on Linux and keeps following them while it runs, as `native_accessibility` does on macOS (`display_preferences`, `sync_preferences`, `crates/app/src/native_accessibility.rs:535-558`, which feed `cx.set_reduce_motion`).
- **Recommendation:** extend the existing settings-portal observer in `desktop_text::portal` (`crates/app/src/desktop_text.rs:697-1100`) rather than open a second connection. The same session, snapshot, deadline and focus refresh read five more values:

  | Namespace | Key | Type | Means |
  | --- | --- | --- | --- |
  | `org.freedesktop.appearance` | `reduced-motion` | `u` | 1 reduce; 0 or unknown no preference |
  | `org.freedesktop.appearance` | `contrast` | `u` | 1 higher; 0 or unknown normal |
  | `org.gnome.desktop.a11y.interface` | `reduced-motion` | `s` (enum) | `reduce` or `no-preference` |
  | `org.gnome.desktop.interface` | `enable-animations` | `b` | false turns animation off |
  | `org.gnome.desktop.a11y.interface` | `high-contrast` | `b` | true is higher contrast |

  Reduce motion when any motion source asks for it (appearance `reduced-motion` = 1, GNOME `reduced-motion` = `reduce`, or `enable-animations` = false). Ask for more contrast when appearance `contrast` = 1 or `high-contrast` = true. The observer's snapshot carries a `DisplayPreferences`; on Linux `native_accessibility::display_preferences()` returns the latest one from a global instead of `None`, so `sync_preferences` stays the one place that calls `cx.set_reduce_motion` on both platforms, and the window's `apply_motion_preferences` runs on each change. No dependency changes: the locked ashpd 0.13.13 already names both appearance keys.
- **Why the GNOME keys too:** on Omarchy the only settings backend is xdg-desktop-portal-gtk 1.15.3, which publishes appearance `contrast` but not appearance `reduced-motion`; it does forward the GNOME namespaces. GTK 4.22 reads the same five sources, so GitTurtle would agree with its GTK neighbours.
- **Contrast** needs an owner decision on what it changes; the proposal is below. macOS reads Increase Contrast today but changes nothing with it ([native accessibility](../native-accessibility.md), line 35).
- **Outside this decision:** `color-scheme` (GPUI's Linux backend already reads it for window appearance; Follow system uses it), `accent-color` (Omarchy themes carry the accent; the GTK backend does not publish it), reduce transparency (no portal key; GitTurtle's surfaces are opaque), Hyprland's own animation switch, and Orca.

## Compatibility and alternatives

- **What Omarchy users get:** Omarchy installs xdg-desktop-portal-gtk and -hyprland, so `contrast` arrives through the appearance key and reduced motion only through the GNOME keys. Omarchy has no switch for any of them, so they stay at their defaults until the person runs `gsettings`; on stock Omarchy the visible effect is nil. GNOME 50 sessions (xdg-desktop-portal-gnome 50+) also publish appearance `reduced-motion`.
- **Observer changes:** subscribe to `SettingChanged` without the arg0 filter and select namespaces in `change()`. One ordered stream keeps the existing reasoning about coupled keys, and the batch and coalescing bounds already cover a busy backend. Add the five values to `Observed` with the same rule as today (an invalid value clears the old one), read them in the same `join!` under the existing deadline, and extend the snapshot's "a signal during the reads wins" mask. A pure resolver maps `Observed` to `DisplayPreferences` (unknown numbers are no preference, per the specification), so it is tested without a bus. Without any portal (a bare X11 window manager), the preferences stay off, as text rendering does without its fontconfig fallback; no `gsettings` subprocess fallback is proposed.
- **Applying it:** `desktop_text::apply` stores the snapshot's `DisplayPreferences` in a global and calls `native_accessibility::sync_preferences`; the root view observes that global and runs `apply_motion_preferences`, as the macOS notification subscription does. Window activation already calls `sync_preferences` and `desktop_text::refresh` together (`main.rs:932-941`). The module comment and `crates/app/AGENTS.md`'s "OS display settings" row then describe the wider observer.
- **Alternatives:**
  - *Appearance keys only:* follows the specification alone, but on Omarchy and any desktop with the GTK backend it never sees reduced motion. Rejected.
  - *A second observer or connection:* duplicates connection, deadline, reconnect and focus-refresh code that `desktop_text::portal` already proves. Rejected.
  - *Reading GSettings or dconf directly:* bypasses the portal, needs the schemas installed and does not work in a sandbox. Rejected.
  - *Hyprland `animations:enabled` (`hyprctl -j getoption`):* Omarchy's toggle exists for GPU-less machines, not as an accessibility preference, and it ties GitTurtle to one compositor's IPC. Not proposed; asking Omarchy to have its toggle also set `org.gnome.desktop.interface enable-animations` would reach every GTK app as well, and is the owner's call.
- **What "more contrast" should change (proposal):** one derived transform, `Palette::with_more_contrast()`, applied inside `Palette::apply` (`appearance.rs:1859`) whenever the desktop asks, for built-in, custom and Omarchy palettes alike, and never saved. Against the rules in [`DESIGN.md`](../../DESIGN.md#semantic-palette-ownership) and the [readability rules](themes/spec.md#readability-rules):
  - secondary text and line numbers move toward `text` until they reach 7:1 on the six surfaces (WCAG 1.4.6), or take `text` where `text` itself is lower; syntax roles are fitted at 7:1 instead of 4.75:1, with the same mixing toward `text`;
  - dividers, `border` and the popup edge step toward the text side until they hold 3:1 on canvas and panel (WCAG 1.4.11), up from 1.3:1 and 1.4:1;
  - resting secondary Buttons, inputs, Switch tracks and chips draw the 1 px edge that `keep_disabled_shape` already gives disabled Buttons, so each control's boundary holds 3:1 instead of resting on a 1.08:1 fill;
  - disabled labels rise from about 3:1 to 4.5:1 and stay below secondary text;
  - unchanged: hues, the 2 px accent focus ring and selection marker (already 3:1), quiet diff tints, icons with words for status, and every size and position (nothing moves).

  The theme editor keeps measuring the saved theme, not the transformed one. Applying the same transform under macOS Increase Contrast would keep the platforms in step; today macOS reads that setting and ignores it.
- **Could change the recommendation:** an xdg-desktop-portal-gtk release that publishes appearance `reduced-motion` (the GNOME fallback then becomes redundant but harmless); Omarchy adding its own accessibility switches; a GPUI release that reads these keys itself (then the app should not set them twice).

## Enforcement and acceptance

- **Owners:** `crates/app/src/desktop_text.rs` (portal reads and resolver), `native_accessibility.rs` (Linux `display_preferences`, a global, `sync_preferences`), `main.rs` (observe the global), `appearance.rs` (the contrast transform, once decided), and the contracts [`docs/native-accessibility.md`](../native-accessibility.md), [`docs/linux.md`](../linux.md#platform-limits) (replace the macOS-only line and the inaccurate "Manual app preferences" claim), [`crates/app/docs/navigation-and-refresh.md`](../../crates/app/docs/navigation-and-refresh.md#desktop-observers) and `DESIGN.md` (contrast rules). The change needs the architecture review (shared state, platform) and, per the owner's parity decision, native evidence; it adds no dependency.
- **Tests, Linux-conditional like the existing portal tests:** `change()` accepts each new namespace and key, ignores others and clears values of the wrong type; a signal for a new key during the initial reads wins over its read; the resolver's truth table (each source alone, absent keys, unknown numbers such as 2 treated as no preference, the OR across sources); the no-portal path leaves reduce motion off. GPUI tests: a snapshot asking for reduced motion sets `cx.reduce_motion()` and pauses GIF playback, and clearing it does not resume playback (as `gif_playback`'s `reduced_motion_pause_keeps_the_current_frame_until_explicit_resume` expects); the first snapshot applies before the window opens. For contrast: every built-in palette and the stock Omarchy mappings meet the raised floors and still pass `readability_issues`, the transform is the identity when not asked for, and a layout test shows nothing moves.
- **Native check on the development host** (proposed, not run on 2026-10-28; record each initial value first and restore it; GTK apps on screen switch style while a key is set):

  ```sh
  # Watch what the portal emits
  busctl --user monitor org.freedesktop.portal.Desktop
  # Reduced motion: the GNOME 50 key, forwarded by xdg-desktop-portal-gtk
  gsettings set org.gnome.desktop.a11y.interface reduced-motion reduce
  gsettings reset org.gnome.desktop.a11y.interface reduced-motion
  # Animations off: what GTK maps to gtk-enable-animations
  gsettings set org.gnome.desktop.interface enable-animations false
  gsettings reset org.gnome.desktop.interface enable-animations
  # More contrast: also emits org.freedesktop.appearance contrast = 1
  gsettings set org.gnome.desktop.a11y.interface high-contrast true
  gsettings reset org.gnome.desktop.a11y.interface high-contrast
  # Read a value back through the portal
  busctl --user call org.freedesktop.portal.Desktop /org/freedesktop/portal/desktop \
    org.freedesktop.portal.Settings ReadOne ss org.freedesktop.appearance contrast
  ```

  Check each before launch and live while the app runs: a GIF in image comparison pauses and Play is unavailable, spinners hold still, turning the preference off does not resume playback, and focus return picks up a change made while the window was inactive. The appearance `reduced-motion` key cannot be produced on this host; it needs a GNOME 50 session (the planned Ubuntu GNOME check) or the unit tests above. `omarchy toggle animations` changes only Hyprland and is expected to leave GitTurtle unchanged.
- **Remaining uncertainty:** the contrast transform's look across palettes (needs the owner's decision, then frames in a dark, a light and an Omarchy palette); KDE, whose portal backend was not checked; macOS parity for the same transform, checked later on a Mac.
