# CI runners and Rust test tools: current facts (2026-11-18)

Research for the CI clean-up, using the [research template](research-template.md). Every fact below was read on 2026-11-18 from the vendor's own page, documentation, changelog, source repository or GitHub's public API, without signing in to any service. Nothing was installed, built or changed, and no account was created. GitHub's own plan, billing and platform facts are in the sibling note `2026-11-18-ci-github-platform-facts.md`; this note covers third-party runners and Rust test tooling only. Prices are US dollars per minute unless a row says otherwise.

## Decision and scope

- **Question:** which runner vendors and Rust test tools the CI clean-up's plan may name, for a public repository owned by a User account, and at what price. The outcome for a contributor is a faster pull-request run (the critical path is `cargo nextest run` on `macos-15`) that still reports every failure.
- **What the facts allow (no recommendation is made here):**
  - Of the vendors asked about, a User account is supported in the vendor's own words by **Namespace** (Linux and macOS), **RunsOn** (Linux only, in the owner's own AWS account) and **Depot CI** (Linux only, a separate CI engine and not GitHub Actions runners). **Blacksmith**, **Depot's GitHub Actions runners** and **WarpBuild** state that they need an organization. **Cirrus Runners** takes no new customers and **BuildJet** has shut down. **Ubicloud** does not say; its source registers runners per repository, which is the mechanism a User account needs, but vendor support for a personal account is not established.
  - Only Namespace is established as a managed macOS option for a User account. Every vendor that registers runners on a repository (the only level a User account has) asks for repository **Administration: read and write**.
  - cargo-nextest partitions by count or hash, not by recorded duration; duration-balanced shards would have to be built by the project from the JUnit `time` values.
  - On stable Rust 1.99 the levers are profile settings (`opt-level`, `debug`, `split-debuginfo`) and, on Linux arm64 only, an alternative linker; `lld` is already the default on `x86_64-unknown-linux-gnu` and incremental compilation is already off under `CI`.
- **What would change the answer:** moving the repository to an organization (opens Blacksmith, Depot runners and WarpBuild), a vendor changing its account rule or price, or nextest gaining a duration-aware partitioner.
- **Outside this note:** GitHub-hosted runner sizes, minutes and prices, larger runners, cache and artifact limits (sibling note); any measurement of this workspace; the choice itself.

Moving CI to any of these is a trust change. A User account has no organization-level runners, so a vendor must register runners on the repository, and RunsOn's documentation states that GitHub requires repository administration for that; Namespace and Ubicloud request the same permission. The organization-only vendors avoid it by using the organization runner permission, which a User account cannot grant.

### cargo-nextest

The newest release is 0.9.152 (2026-11-13); the repository pins 0.9.146 (2026-09-21), five published releases behind (0.9.147 was not finalized), and the gap includes two security fixes and a 0.9.151 scheduling fix for test groups combined with `threads-required`. `--partition` has three forms: `slice:m/n` (round-robin over all tests of all binaries, applied after filters, the documented choice for even shards), `hash:m/n` (stable membership, uneven for small sets) and the deprecated per-binary `count:m/n`. Nextest cannot shard by recorded duration, and its documentation suggests nothing beyond `slice:`; a duration-balanced split would be the project's own tool reading the JUnit report (`<testcase time="…">`, written to `target/nextest/<profile>/junit.xml`) and passing each shard a filterset, since the libtest JSON stream is still experimental. `cargo nextest archive --archive-file` lets one job build and several run: each shard needs the archive, the same revision checked out, the same nextest version and, when the checkout path differs, `--workspace-remap`; the archive carries binaries for the triple it was built for and no source. Test groups cap concurrency for named sets of tests with `max-threads`, and `threads-required` weights heavy tests.

### Faster test build and run on stable Rust

`lld` has been the default linker on `x86_64-unknown-linux-gnu` since 1.90.0, so x86-64 Linux jobs already have it at 1.99; `aarch64-unknown-linux-gnu` still uses the system linker, where Cargo's guide suggests LLD, mold or wild through `rustflags`, and nothing read today changes the default on `aarch64-apple-darwin`. Cargo documents per-package `opt-level` overrides and says only to "experiment with different levels"; it gives no advice for a workspace's own crates under test, so raising them from 0 trades a longer build for a shorter run and has to be measured. Its build-performance guide recommends `debug = "line-tables-only"` for workspace members and `debug = false` for dependencies; on macOS Cargo defaults `split-debuginfo` to `unpacked`, which leaves debug information in the object files, where rustc's own `packed` default produces a `.dSYM`. Since Cargo 1.99, incremental compilation is off whenever `CI` is set, so `CARGO_INCREMENTAL=0` is redundant there but harmless. sccache 0.19.0 can store objects in the GitHub Actions cache, but it reuses a crate only while all of its sources are unchanged and cannot cache crates that are linked, so for a workspace dominated by one large crate and one test executable it adds little over a dependency cache: that last step is an inference from its documented rules, not a vendor statement or a measurement.

### macOS runner supply

GitHub states at most 5 concurrent macOS jobs on standard runners for Free, Pro and Team plans (50 on Enterprise) and warns that macOS jobs "may take longer to start" in high demand. Blacksmith claims no concurrency limit and macOS "available on demand"; Depot says its macOS capacity "is not fully elastic" and can queue longer under demand; WarpBuild asks customers to contact support for high macOS concurrency; none of the three accepts a User account. Namespace caps macOS at 12 vCPU on the Developer plan (two 6-vCPU or three 4-vCPU runners at once), 24 on Team and 48 on Business, and names concurrency limits as the usual cause of queueing. GetMac allows 1 concurrent VM on its two smallest plans. No vendor publishes a queue-time figure.

### Evidence that could change this

A live install attempt on a User account for Namespace or Ubicloud; a vendor price change; a nextest release with duration-aware partitioning; a Rust release that makes `lld` the default on another target.
