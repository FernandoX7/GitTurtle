# Linux AVIF, HEIF/HEIC and JPEG 2000 (2026-10-28)

Research for the owner decision of 2026-10-28 in [full Omarchy support](omarchy-full-support.md) (item 9: Linux reaches feature parity with macOS where possible), using the [research template](research-template.md). Base revision: `c219a6f`.

## Decision and scope

- **Question:** how a Linux build decodes AVIF, HEIF/HEIC and JPEG 2000 previews, which macOS decodes through ImageIO, within the preview crate's bounds and with no GPL code.
- **User-visible outcome:** these images render in the existing image comparison (side by side, Overlay, Wipe, zoom) instead of reporting a macOS codec requirement. Open in default app stays available either way.
- **Recommendation by format:**
  - **JPEG 2000: adopt `hayro-jpeg2000` 0.4.1.** It is pure Rust, `Apache-2.0 OR MIT`, `forbid(unsafe_code)`, and the same crate the [PDF note](2026-10-28-linux-pdf-pages.md) uses for JPX streams. Preflight with GitTurtle's existing SIZ reader, decode at reduced resolution, and enforce a sample budget before `decode`.
  - **AVIF: adopt `mp4parse` 0.17.0 for the container and `dav1d` 0.11.1 over the system libdav1d** (BSD-2-Clause; 1.5.4 on Arch and Arch Linux ARM). Set an explicit frame-size limit, thread count and frame delay. Do **not** use `image`'s `avif-native` feature: it decodes before limits apply and ignores orientation.
  - **HEIF/HEIC: defer.** Keep Open in default app. Three things block it: the HEVC patent question, which only the owner can answer; the fact that the only established decoder stack (libheif with libde265) is LGPL-3.0, and Arch's libheif build also links GPL x264/x265; and the fact that every pure-Rust HEVC decoder was first published in 2026. Re-evaluate `zune-heic` against a maturity gate (Enforcement below).
- **What would change the answer:**
  - the owner accepting a specific LGPL or patent position;
  - `zune-heic` or another permissive HEVC decoder passing the gate;
  - upstream `hayro-jpeg2000` adding a memory budget (removes a preflight);
  - a wish to ship bundles with no system codec library (favors `avif-decode`/`rav1d` for AVIF).
- **Outside this decision:** HDR tone mapping, depth and auxiliary images, image sequences (AVIS, HEIF bursts), JPEG XL, macOS, and PDF pages ([separate note](2026-10-28-linux-pdf-pages.md)).

## Compatibility and alternatives

- **Pinned stack:** Rust 1.99.0, `image` 0.25.10 shared with the toolkit, `zune-core` 0.5.3, `moxcms` 0.8.1. Every recommended crate license (`Apache-2.0 OR MIT`, MIT, MPL-2.0, BSD-2/3-Clause) is already on [`deny.toml`](../../deny.toml)'s allow list. Declaring the new dependencies under `[target.'cfg(target_os = "linux")'.dependencies]` keeps macOS on ImageIO.
- **System libraries:** cargo-deny sees crate licenses only. A system C library (libdav1d now, any libheif later) must be recorded in `THIRD_PARTY_NOTICES.md`, `docs/licenses/dependencies.json` and the [Linux guide](../linux.md)'s runtime and build lists (and the CI and AUR dependency lists).

### HEIF/HEIC: what the owner must decide

1. **Patents.** HEVC is licensed through commercial pools, and the Access Advance page names software among the covered products. That is true for every decoder, including pure Rust. In-app HEIC decoding needs the owner's position (or legal advice) first. AV1 does not raise the same question, given the AOMedia royalty-free license.
2. **LGPL, if libheif/libde265 is ever chosen.** It is not recommended here. LGPL-3.0 code can be used by MIT GitTurtle only if:
   - it is **dynamically linked**, so a user can replace it;
   - its license and notices are shipped;
   - its corresponding source is provided or offered **if GitTurtle distributes the binary**;
   - modification for debugging that replacement is not prohibited;
   - its parts are recorded outside `deny.toml` (cargo-deny does not see C libraries).
   
   The libheif must also be a custom build with **only** libde265 enabled (x264, x265, ffmpeg and the other encoders and plugins off). Arch's package links GPL x264/x265, which the no-GPL rule excludes, and `libheif-sys`'s `embedded-libheif` compiles those encoders in whenever they are installed. The owner must decide whether any LGPL component is acceptable. This note does not choose it.
3. **glycin, if wanted.** It keeps HEVC and libheif out of GitTurtle's process and sandboxes them. But it brings LGPL GLib into the process, and it relies on a system loader that runs GPL-linked libheif. That is a question of whether calling system GPL code over IPC is acceptable; GitTurtle's Open in default app already hands bytes to arbitrary desktop applications.

**Could change the HEIF deferral:** the owner settling (1). Then `zune-heic` passing the maturity gate below, which favors it over (2) and (3) because it is permissive, in-process and needs no system codec.

## Enforcement and acceptance

- **Owners:** `crates/preview` (Linux arms of `decode_image`; a target-gated `jpeg2000.rs` reused on Linux and extended to report component count; new `avif` and `jpeg2000` decoder modules returning straight RGBA8 with original dimensions after orientation). Update [`docs/file-previews.md`](../file-previews.md) rows, [`crates/preview/AGENTS.md`](../../crates/preview/AGENTS.md), `THIRD_PARTY_NOTICES.md`, `docs/licenses/dependencies.json`, and the [Linux guide](../linux.md)'s build and runtime package lists, the CI apt and pacman lists and the AUR `depends` (libdav1d). Architecture review for a new system library; [security review](security-review.md) before integration (decoders).
- **Tests (fixtures with provenance in `crates/preview/tests/fixtures/README.md`):**
  - AVIF: 8-bit and 10-bit, alpha (straight and premultiplied), `irot`/`imir`, a grid (explicit refusal), and a crafted sequence header above `frame_size_limit` (refused before allocation);
  - JPEG 2000: JP2 and raw J2K (the existing `half-red-blue` fixtures), a large lossy JP2 decoded at reduced resolution, a palette JP2 above the budget (refused), the #1549 and #1649 reproductions (explicit errors, no abort or panic escaping);
  - a test that the macOS path is unchanged.
- **Release measurement** (release build on the AArch64 Asahi host and an x86-64 Linux host; record fixture, hardware, cold or warm, p50/p95/max over at least 20 runs, peak RSS and thread count):
  - decode to the 1,600-px app edge for a 4032 × 3024 AVIF (8-bit), a 10-bit AVIF with alpha, a 6000 × 4000 JP2 (reduced and full resolution), and a raw J2K;
  - comparison against the existing PNG/JPEG path on the same images, so the new formats can be judged against current latency;
  - executable size delta and the new dynamic `NEEDED` entries (`readelf -d`).
- **HEIF/HEIC re-evaluation gate** (planner task, after the owner's patent decision):
  - `zune-heic` has at least three months of releases with no unresolved crash reports;
  - a GitTurtle-run fuzzing campaign (the upstream target plus GitTurtle's bounds) of agreed duration finds no crash, hang or over-budget allocation;
  - output matches macOS ImageIO on iPhone grid, Samsung, monochrome and alpha fixtures;
  - 10-bit files are refused explicitly.
  
  Until then, HEIF keeps "Open in default app" and the current Linux wording.
- **Remaining uncertainty:** `mp4parse`'s crates.io release staleness against Firefox's in-tree use; whether `hayro-jpeg2000` colour conversion (ICC and CMYK) matches ImageIO closely enough; libdav1d's presence on non-Arch systems for bundles.

## Outcome

Not implemented. JPEG 2000 and AVIF await implementation tasks; HEIF/HEIC awaits the owner's patent and licensing decisions.
