# Linux GitHub account in the Secret Service (2026-10-28)

Research for the owner decision of 2026-10-28 in item 9 of phase 3 of [full Omarchy support](omarchy-full-support.md#phases) ("Pull-request review: store the GitHub account in the Secret Service"), using the [research template](research-template.md). Code references are at `c219a6f`; nothing was built or changed.

## Decision and scope

- **Question:** how GitTurtle stores the GitHub account that the GitHub panel uses on Linux, so pull-request review works with a live account there as it does on macOS. Today `SecureStore` on Linux loads nothing and refuses to save ("Secure GitHub credential storage is not yet available on this platform. No plaintext credential was stored.", `crates/app/src/github/transport.rs:146-158`).
- **Recommendation:** implement the Linux `CredentialStore` with **`oo7` 0.6.0 used directly**, through its `oo7::dbus` client (`Service`, `Collection`, `Item`), not its `Keyring` wrapper and not GPUI's `cx.write_credentials`. Declare it with the toolkit's exact features, `oo7 = { version = "=0.6.0", default-features = false, features = ["async-std", "native_crypto"] }`. It is already in the graph and in the shipped Linux binary through `gpui-pre-linux` 0.3.4, so `Cargo.lock` gains no package and `deny.toml` needs no change. It is pure Rust, MIT, on the same zbus 5 and async-io runtime as the app's portal code, and it negotiates the encrypted transfer session the specification defines.
- **Behaviour:** one item in the default collection, holding the same JSON `{login, token}` bytes the macOS item holds. A stored read (Refresh, opening a PR) never asks for a prompt: a locked keyring, a missing service or a malformed item is an error with guidance. Explicit **Connect GitHub CLI account** may show the keyring's own unlock or create-keyring prompt, and **Disconnect GitTurtle** may show a delete confirmation. Every failure fails closed: no plaintext file, no other fallback.
- **Outside this decision:** the macOS Keychain path (unchanged), the GitHub CLI's own token storage, Git credential helpers for fetch/pull/push, Flatpak packaging (see the portal row below), Windows, and token revocation.

## Compatibility and alternatives

- **Pinned stack:** Rust 1.99, GPUI Kit 0.6.0, `gpui-pre-linux` 0.3.4, oo7 0.6.0, zbus 5.19.0, ashpd 0.13.13 (`async-io`), async-io 2.6.0. Both Linux targets already compile oo7 for the toolkit, so AArch64 and x86-64 build it today; it uses RustCrypto (`native_crypto`), no C library and no OpenSSL.
- **Runtime fit:** keep `CredentialStore` synchronous and drive oo7's futures with `futures::executor::block_on` inside the operation job, as `security-framework` calls run there now. zbus's own executor thread and async-io's reactor wake it; nothing runs on the UI thread or blocks GPUI's background executor. Bound every call with a deadline and the job's `OperationControl` (a timer from the already-locked async-io 2.6.0, selected against the oo7 future). Proposed bounds: 5 s for a stored read, which never prompts; 120 s for Connect and Disconnect, which may (gh uses 60 s for the same calls). Keep the process-wide `try_lock` on Linux too, so a second window's call fails at once instead of opening a second unlock prompt. Open one session connection per credential call; they are rare and a fresh connection survives a restarted daemon.
- **Item schema** (mirrors the macOS service and account, and the `service`/`username` pair that go-keyring and keyring-rs use for the same pair, so `secret-tool` and either library find it):

  | Field | Value |
  | --- | --- |
  | Collection | the `default` alias ("Login" on GNOME, "Default keyring" on Omarchy); never `session` |
  | `xdg:schema` | `com.gitturtle.github.oauth` |
  | `service` | `com.gitturtle.github.oauth` (macOS `SERVICE`) |
  | `username` | `github.com` (macOS `ACCOUNT`) |
  | Label | `GitTurtle GitHub authorization (github.com)` |
  | Secret | the macOS JSON bytes, `text/plain` (UTF-8, which KWallet's Secret Service requires) |

  Search with all three attributes; create with `replace = true`.
- **Failure behaviour:**

  | Condition | Stored read (Refresh, open PR) | Connect / Disconnect |
  | --- | --- | --- |
  | No session bus, or no `org.freedesktop.secrets` owner or activation (`ServiceUnknown`) | Error: no Secret Service answered; start the desktop keyring. | Same; nothing stored. |
  | No `default` alias | `Ok(None)` (nothing GitTurtle saved can be there) | Connect: `default_collection()` creates one, through the provider's prompt |
  | Collection or item locked | Error naming the locked keyring; no `Unlock` call | `unlock(None)` shows the keyring's prompt |
  | Prompt dismissed, deadline, or Cancel | — | Error; nothing stored, or "may remain stored" after a late cancel, as macOS reports |
  | Item JSON invalid | "The GitHub keyring entry is invalid. Connect the account again." | Connect replaces it |
  | More than one match | Error; Disconnect removes every match | Disconnect deletes each |
  | DH negotiation refused | oo7 retries with `plain` (same-user session bus) | same |

  Saving reads the item back and compares login and token before reporting success, as `verify_saved_credential` does on macOS. User-visible text names "your desktop keyring" on Linux, behind the platform check the crate guide requires (`github_view.rs:795`, `connect_existing`'s late-cancel message, `docs/github-collaboration.md`).
- **Alternatives:**
  - *GPUI `cx.read_credentials`/`write_credentials`:* already linked, but it labels every item `zed-github-account`, calls `unlock()` (a prompt) before every read, and on macOS writes a different Keychain item class from GitTurtle's existing one. Rejected.
  - *oo7 `Keyring` wrapper:* simplest API, but `Keyring::new()` creates the default collection, through the provider's prompt, whenever the `default` alias is missing, so even a stored read could prompt; and under Flatpak it silently switches to a different, file-backed store. Use the `dbus` client, which separates `with_alias` (no creation) from `default_collection`.
  - *keyring 4.2.0:* a portable façade, but its Linux store unlocks (prompts) on every search, needs a runtime/crypto feature choice, and adds keyring, keyring-core, the store crate, secret-service and a second RustCrypto major (aes 0.9, cbc 0.2, hkdf 0.13). Rejected.
  - *secret-service 5.2.0 directly:* same new packages and crypto majors as above, and a zbus 6 migration in flight. Rejected.
  - *dbus-secret-service 4.1.0:* synchronous, but links the C libdbus (AFL-2.1 OR GPL-2.0-or-later, used under AFL-2.1, which `deny.toml` does not allow and cargo-deny cannot see), adds `libdbus-1` to the package's runtime and build dependencies, or bundles C with `vendored`. Rejected.
  - *Direct zbus to `org.freedesktop.secrets`:* no new package, but it would reimplement the DH session, secret encoding and prompt handling that oo7 already ships in the binary. Rejected unless oo7 is dropped by the toolkit.
  - *Secret portal (`org.freedesktop.portal.Secret`):* only for a sandboxed (Flatpak) build, where the app gets a per-app master secret and keeps its own encrypted file. Not applicable to the planned tarball and AUR packages. If a Flatpak is planned, that is a separate decision: oo7's file backend implements it, but it is a different store from the host keyring, and Omarchy routes the portal to gnome-keyring only on `quattro`.
- **At rest on Omarchy:** the default keyring is passwordless and gnome-keyring keeps its secrets unencrypted in the keyring file, as it does for the GitHub CLI's own token. GitTurtle writes no file itself and cannot detect this through the API, so the contract "no plaintext credential is written by GitTurtle" holds, but the UI and docs must not claim encryption. `.claude/rules/persistence.md` ("never written to disk on Linux") needs rewording to say GitTurtle never writes them.
- **Could change the recommendation:** a `gpui-pre-linux` release that drops oo7 or moves to oo7 0.7 or zbus 6 (then match it, or reconsider direct zbus); an oo7 0.6.x release with the prompt `ok_or_else` fix (take it); a decision to ship a Flatpak; an owner decision to refuse storage on passwordless keyrings.

## Enforcement and acceptance

- **Owners:** `crates/app/src/github/transport.rs` (`SecureStore` for `cfg(target_os = "linux")`, the shared try-lock, error mapping), `github_view.rs` (platform wording), `crates/app/Cargo.toml` (Linux target dependency), and the contracts `docs/github-collaboration.md` (account storage paragraph and the "not yet present" sentence), `docs/linux.md#platform-limits`, `README.md` Linux gaps, `docs/authentication.md` limits, `.claude/rules/persistence.md`. The change needs the architecture review (persistence, platform), an independent [security review](security-review.md) before integration (credentials), and a release measurement and native evidence, per the owner's 2026-10-28 parity decision.
- **Dependency checks:** `Cargo.lock` must change only in `gitturtle`'s own dependency list; `cargo deny --locked check` and `scripts/collect-third-party-licenses.py` for both Linux targets must show no new package or notice.
- **Tests, always run on Linux:** put the oo7 calls behind a small backend trait so the logic is testable without a bus. Then: the stored read on a locked collection returns the locked-keyring error and never calls `unlock` or a prompt; a backend future that never completes ends at the read deadline, and a cancelled Connect returns promptly; a second window's call is refused while the lock is held (mirror `another_window_keychain_operation_is_refused_without_waiting_or_touching_credentials`); the save path rejects a read-back with another token; invalid JSON, duplicates and `ServiceUnknown` map to their messages, none of which contains the token; the attribute set and label equal the table above and the macOS constants; Linux visible text and accessible labels never say "Keychain" (as `authentication.rs` tests do).
- **Hermetic integration test, opt-in `#[ignore]` on Linux:** a private `dbus-run-session` with `gnome-keyring-daemon --components=secrets --unlock` fed a test password and a disposable `HOME`/`XDG_DATA_HOME`, as the zbus keyring store's CI does. It covers save/load/remove round trips, a locked collection (gnome-keyring 50.0's `Service.Lock` returns the empty prompt `/`, `daemon/dbus/gkd-secret-service.c:597-610`) refused without blocking past the bound, a bus with no provider, duplicate items, and an invalid item written by the test. It needs `dbus` and `gnome-keyring` on the runner; the Linux CI job installs neither today.
- **Native evidence on the Omarchy host:** with an owner-authorized GitHub account, Connect, restart, Refresh and open a PR without a prompt; Disconnect; inspect the item's label and attributes with `busctl` (`Collection.SearchItems`, `Item.Attributes`) rather than `secret-tool search`, which prints the secret; then a password-protected, locked keyring for the refusal and the unlock prompt (gcr's prompter on Hyprland, not yet seen). A release measurement of the stored read (connect, DH session, search, secret) records host, cache state and tail latency; the path is not hot, but the parity decision asks for one.
- **Remaining uncertainty:** the unlock prompt's appearance on Hyprland; KWallet and KeePassXC behaviour (KeePassXC can confirm reads itself, so its stored reads may hit the 5 s bound); upstream x86-64 Omarchy.
