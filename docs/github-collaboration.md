# GitHub collaboration

GitTurtle’s repository-header **Pull requests** control and **GitHub pull requests…** command open a native panel for the selected local worktree. Overview, Files, and Review keep the captured PR context, conversations, and collected feedback together. Opening the panel reads local remotes and saved drafts only. The initial read is deferred until GPUI finishes the parent view update, so command-palette activation cannot recursively borrow the repository view; a panel closed before that callback skips the read. An interrupted initial local read resumes on warm reopen without replacing edited destination or draft fields. Connect, Refresh PRs, selecting a PR, refreshing or paging conversations, reviewing a new PR destination, and Send to GitHub are explicit network interactions. Opening a reply composer, restoring text, local filesystem refresh, and repository focus do not contact GitHub.

A create form with an invalid destination reports the required `owner/repository` format. Title and body edits remain in the open form, and its status explicitly says the draft is not saved until the destination is valid. Correcting that field queues the retained text for local saving; clicking New pull request again preserves an already open create form. A delayed save reply cannot mark the current invalid destination as saved. Missing PR selection is reported separately from destination validation.

The current provider is GitHub.com. Ordinary Git authentication, profiles, branch Push, hooks, filters, and signing retain their existing paths. PR creation requires an already published branch and never pushes it implicitly.

## Account connection

GitTurtle uses the supported [GitHub CLI browser authentication flow](https://cli.github.com/manual/gh_auth_login), followed by an explicit **Connect GitHub CLI account** handoff. **Copy sign-in command** provides `gh auth login --hostname github.com --web --skip-ssh-key` for a user-driven Terminal sign-in. Keep existing Git choices when the CLI asks about Git configuration; GitTurtle does not invoke `auth setup-git`, upload SSH keys, switch the CLI account, or request credentials in conversation. The installed CLI must be available at `/opt/homebrew/bin/gh`, `/usr/local/bin/gh`, or `/usr/bin/gh`.

Connect reads the CLI’s current GitHub.com token through a bounded pipe, verifies the account with `/user`, and stores a separate credential in macOS Keychain under service `com.gitturtle.github.oauth`. GitTurtle never enables the CLI’s insecure-storage option and never writes tokens to ordinary preferences, Git profiles, drafts, arguments, or diagnostics. Runtime API processes receive the token only in their transient environment. The native Keychain API may require an explicit user unlock or access decision. Disconnect removes only GitTurtle’s Keychain item; it does not revoke the account or log out the CLI.

API subprocesses use an absolute `https://api.github.com/` destination and a fresh private, empty `GH_CONFIG_DIR`, removed after the process finishes. CLI `api_host` and `http_unix_socket` configuration cannot reroute GitTurtle's credential. The explicit CLI token handoff retains the user's CLI configuration; ordinary Git authentication and system HTTPS proxy/TLS configuration retain their existing behavior. HTTP redirects remain governed by the installed CLI and its HTTP library, so fixing the initial origin is not an application-owned redirect allowlist.

The credential store is a platform abstraction. Linux builds remain portable, but a Secret Service implementation is not yet present; connection refuses persistence instead of falling back to a plaintext file. CLI OAuth itself, actual Keychain unlock, and hosted account authorization require separate environment-dependent validation.

## PR inspection and creation

PR lists load 50 open PRs per explicit page, up to page 1000. Pages replace the visible list. Server pagination links only indicate that another page exists; their URLs are never followed. The API destination remains the captured GitHub.com repository. As with the provider’s REST pagination, the list is live and may shift when new PRs are created between page requests.

Selecting a PR loads current title, exact description source, draft/open state, head/base branches and complete commit identities. The explicit selection separately loads review history, check runs, commit statuses, the first changed-file page, and the first authoritative conversation page. Each status endpoint is bounded to 100 entries; additional entries or partial endpoint failures are explicitly reported. Older-head reviews are identified. These entries report provider results and do not infer an aggregate approval decision or merge authorization.

New PRs support title, exact description text, Draft or Ready, destination base, and a published head. An `owner:branch` head resolves the same repository name under the named owner. Creating from a differently named fork repository is outside the current form. **Review outbound action…** resolves the published branch identities and shows them with the account and destination. **Send to GitHub** rechecks those identities, refuses moved branches, and makes one create request. The REST create endpoint accepts branch names rather than a conditional head SHA, so the small interval between the final check and provider acceptance is not an atomic ref lock.

**Load local base templates** reads supported Markdown template paths from the selected locally available base revision: `pull_request_template.md` in the root, `docs`, or `.github`, and Markdown files immediately inside the corresponding `PULL_REQUEST_TEMPLATE` directory. Matching is case-insensitive. The selected source revision is shown, regular Git blobs are used, symlinks are ignored, and working-file edits cannot change the captured template. Up to 32 templates and 256 KiB per template are supported. Choosing a template appends its exact text. A missing local base asks for an explicit Git fetch or a locally available base name; it never downloads objects automatically.

**Open captured local comparison** in Overview compares the captured base/head using their local common ancestor through the existing core comparison and navigation. It requires the head, base and merge-base objects locally. Missing objects produce actionable guidance; no implicit checkout, fetch, branch creation, or staging occurs. Closing the PR panel cancels the local comparison request and suppresses late presentation.

## Comments, reviews, and local recovery

The native Review section supports discussion-only comments and collected reviews with Comment, Approve, or Request changes. Approval and change-request permissions remain GitHub’s decision. Comment reviews can collect inline feedback without a summary; Request changes requires a summary. Every submit confirmation shows the account, repository, PR number, full head/base identities, event, summary, and every inline comment with its captured path and position. The service rereads the PR before posting and refuses moved head/base identities or a closed PR. Reviews include the captured `commit_id`; if a head moves after the check, the review remains associated with the reviewed commit. Positions are never silently remapped.

**Files** provides a native changed-file list, a virtualized unified patch, exact patch Source, and file-specific Threads. Explicit pages contain up to 100 files, within GitHub’s 3,000-file endpoint limit. File pages replace the visible page. Metadata retains bounded raw patches; only explicit file selection prepares line rows on the worker. Switching files, replacing a page, or closing cancels replaceable preparation, and generation checks reject late results. Each page is bracketed by captured-head/base checks; a moved identity refuses the result. These reads use provider-supplied patches and do not fetch Git objects or require a local checkout of the PR branch. **Open captured local comparison** remains available for locally present text, images, documents, and other supported content.

Click a changed line, or use Up/Down in the patch list. Shift-click or Shift-Up/Down extends a range; Return or **Comment on selection** opens the inline composer. Supported ranges contain consecutive added lines or consecutive deleted lines on one side of one hunk. Cross-side selections, context-only selections, hunk boundaries, malformed/truncated patches, and unavailable binary patches cannot become inline positions. Parsing verifies hunk counts and the reported total additions/deletions, with a 20,000-row inline limit. Source preserves the exact supplied patch, including when inline anchoring is refused. Added/deleted signs and separate Before/After line numbers accompany the themed backgrounds. The keyboard-focused list outline remains distinct from selected lines.

**Add to review** collects a comment locally. Review shows all collected positions and text, with Edit and Remove actions. A separate unfinished composer is also saved; submission asks the user to add or discard it. File and section navigation keep that composer attached to its original captured position. Collected reviews support at most 100 inline comments and use optional `start_line`/`start_side` for ranges. Discussion-only posting is disabled while inline feedback is present, avoiding an accidental submission that omits it.

Overview and file-specific Threads use GitHub GraphQL `PullRequestReviewThread` identities, resolution state, outdated state, and viewer permissions. Resolved/unresolved labels come from the provider; REST comment grouping never establishes conversation state. Each explicit page requests at most 25 conversations with 20 comments per conversation. **Next comment page** requests at most 100 comments for one captured thread and replaces its visible comments; **Refresh thread** returns to its opening page. The opening comment is requested separately on every thread read, preserving its identity even when the displayed comments are a later page. Conversation pages replace the visible list, retain bounded Previous/Next cursor navigation, and stop at 1,000 pages per inspection. Opaque cursors are limited to 1,024 bytes; missing, repeated, empty, or inconsistent continuation metadata is refused with explicit refresh guidance.

Outdated conversations retain their original commit and Before/After positions, including supplied range sides, independently of the current PR head. A deleted author is labeled Deleted account. A missing opening comment or nullable comment node leaves available text readable and identifies incomplete context; replying remains disabled. A missing conversation node, malformed response, or GraphQL error refuses that response rather than presenting a partial page as complete. File-specific Threads reports only conversations on the loaded page, so an empty file view does not assert that no conversations exist elsewhere.

**Reply** opens a focused composer attached to the captured conversation. **Review reply…**, **Resolve**, and **Reopen** prepare a confirmation naming the account, repository, PR, full head/base, and exact thread; the reply confirmation includes its complete text. **Send to GitHub** rereads the connected viewer, repository/PR/thread membership, opening comment, path, original commit, PR branches and head/base, and relevant permissions before one mutation. Changed account or target identities and closed PRs refuse the action without remapping. The mutation addresses the captured thread node ID. There is no atomic head/ref lock between this preflight and GitHub accepting the mutation. Success requires matching returned reply identities or thread resolution state; unavailable or mismatched success data is uncertain. After success, refresh explicitly to load current comments and permissions. Reviewer assignment, merging, and changing an existing PR between draft and ready remain outside this panel.

Text drafts use `github-drafts.json` in the application data directory, separately from account credentials. Typing replaces one pending form snapshot and saves after 500 ms of quiet, avoiding a stored draft for every destination or branch-name prefix. Explicit form transitions, review, close and app quit flush the current valid snapshot; previously accepted destination drafts remain separate. Saves use the existing coalesced, serialized preference executor and atomic replacement. The store retains up to 128 draft identities and 16 MiB, refuses overflow, and preserves corrupt or unsupported stores for recovery. Review identities include repository, PR number, head and base. Matching summary, discussion-only/review mode, event, collected comments, ranges, and unfinished composer restore on selecting the same captured PR. Changing a destination flushes the old captured pending review before clearing its identity, including inside the typing quiet period. Older-head drafts remain copy-only: **Copy complete draft** includes summary, event, complete identities, all collected inline text/positions, and unfinished comment text. Creation recovery includes both title and description. **Discard saved draft** removes only the selected stored snapshot; an open edited form can save its text again. Nothing clears text merely because a network request failed.

Reply drafts have an independent quiet-period snapshot and share the serialized saver with review/create drafts. Their collision-safe identity includes the account login and stable viewer node ID, repository name and node ID, PR number and node ID, full captured head/base, thread node ID, path, opening comment ID, and original commit. File/section navigation, switching conversations, panel closure, repository-tab changes, and shutdown flush or retain that exact target and text. A restart restores a reply only when explicit PR/thread inspection supplies the same complete, reply-capable context and account. Drafts for another head/account, deleted or unavailable context, and unloaded conversation pages remain recoverable through their original identities and **Copy complete draft**; no target is silently reassigned. Returning to a valid conversation and choosing Reply restores its saved text. **Save and close reply** preserves the draft locally without a request.

Closing and reopening the panel in the same application window retains the selected PR, file, section, conversation page, scroll handles, source editor, and composers through a per-worktree warm cache. Reopening a retained capture performs no network request; a canceled selected-file preparation may resume locally. The cache keeps at most eight panels and evicts least-recently-used panels above 32 MiB of counted model/text payload, including conversations, templates, attempt messages, current drafts, and conservative editor-text copies. This is a logical retention bound, not process/GPU allocation accounting. Evicted panels and app restarts recover their durable drafts after explicit PR selection. Visible content owns focus after section/source/thread changes; Return and row-navigation bindings are scoped to the PR lists, so they cannot activate the underlying repository. The modal’s width and scrollable body adapt to the actual viewport while retaining its footer. Focusing an inline/reply composer, review summary, or outbound confirmation reveals it in the outer viewport once; subsequent manual scrolling remains under user control.

Accepted outbound work uses the existing serialized operation executor and survives a dropped UI reply. Before sending, it records a pending attempt in the independent `github-attempts.json` file, then records the observed result. This file retains the latest attempt per captured destination/account, bounded to 128 destinations and 1 MiB. An interrupted process can leave a pending record, which the next panel opening shows. Accepted actions are never automatically replayed. The active panel keeps its captured destination visible and requires the action to finish, or explicit cancellation to finish, before closing normally.

A confirmed reply outcome also records a SHA-256 receipt of its exact captured identity and body in the bounded attempt record. Recovery checks these receipts before restoring text, so failure of draft-cleanup saves cannot revive known completed replies as unfinished, including when another reply succeeds while saves still fail. Pending, failed, and resolve/reopen attempts retain earlier receipts; later confirmed replies append distinct receipts. The store preserves up to 128 receipts per destination within its 1 MiB total allowance, accepts legacy single-receipt entries, and refuses overflow without dropping proof. An attempt carrying receipts is never evicted to make room for another destination; only entries without receipts follow the existing destination-eviction policy. No receipt is retired without proof of durable cleanup, and the current implementation conservatively retains them. A full protected store refuses a new pending attempt before dispatch; failure to record an additional successful outcome requires explicit verification against GitHub.

Successful reply cleanup queues an empty snapshot through the same draft saver as typing and removes only that captured reply entry. It cannot overtake an earlier accepted save or clear newer text. Empty replies release draft capacity before other identities in the same atomic batch are added. Receipts do not duplicate reply bodies or credentials.

Draft and attempt reads use the shared descriptor-based bounded app-data reader. A coalesced draft batch merges all pending identities before one atomic replacement; an entry or byte overflow preserves the previous complete store. Attempt writes check the encoded JSON byte limit, including escaped text, before replacement. A pending-record save failure prevents dispatch, and an outcome-record save failure preserves the earlier pending record and requires explicit verification of the remote outcome.

Cancellation, transport deadlines, lost responses, server failures, and invalid success responses may leave an uncertain remote outcome. The panel preserves text and asks the user to inspect GitHub before submitting again. A success response followed by a local outcome-save failure also requires verification rather than replay. Authentication expiry, permission refusal, validation failure, and rate limits have distinct guidance. Rate-limit reset and retry-after headers are reported without automatic retry.

## Bounds and evidence

Requests use the [GitHub CLI API interface](https://cli.github.com/manual/gh_api), fixed GitHub.com routing, REST version `2026-03-10`, and fixed GraphQL queries/mutations with separately supplied variables. Network work stays on the operation thread. Subprocess I/O is nonblocking and drained under a 90-second API deadline (30 seconds for token handoff), an 8 MiB response limit, and 64 KiB diagnostic/header limits. Explicit cancellation kills and reaps the process group. Diagnostics are discarded rather than displaying potentially sensitive CLI output. GraphQL errors are checked even under HTTP 200; permission, authorization, and rate-limit guidance does not schedule a retry.

`cargo test --locked -p gitturtle github` exercises changed-line/range selection and refusal, incomplete and absent patches, renamed paths, fixture isolation, legacy single-line decoding, inline-only collected reviews, mid-read head movement, unfinished/invalid submission refusal, complete draft roundtrips, actual GPUI Return/range composition, warm reopening across an interrupted local read, template-driven cache eviction, minimum-window composer visibility, rapid file replacement and destination-change flushing, and the existing repository/URL validation, pagination without following foreign links, moved-head review refusal, moved-base create refusal, captured review commit/side/line, draft/ready creation fields, cancellation before dispatch, cancellation of a live subprocess, request-body EOF, bounded output, rate limits, expired authorization, no replay after a simulated lost write response, exact draft recovery, and preservation of an invalid draft store. These are fixture and local-process tests; they are not evidence of a real GitHub write, Keychain access, native VoiceOver use, or hosted CI.

Conversation regressions cover authoritative resolved state, exact root/node/account identities, current and outdated positions, permission refusal, independent comment pagination, missing/partial context, malformed and uncertain mutation responses, cursor refusal, and cancellation without replay. Draft regressions preserve all captured identity fields and exact Unicode/whitespace, distinguish changed targets and separator-containing paths, retain previous stores after failed batches, serialize completion behind an in-flight text save, and suppress a completed reply after cleanup failure. The native fixture's model tests exercise reply → explicit refresh → resolve → refresh → reopen against its stateful provider. Current executable, native interaction, and live GitHub evidence belong in the [validation record](validation.md#current-validation-guidance).

## Offline native review fixture

For native interaction QA, launch the executable explicitly with `GITTURTLE_GITHUB_FIXTURE=review` and a disposable local worktree, then open **Pull requests**, choose **Refresh fixture PRs**, and open #42. For an installed build:

```sh
GITTURTLE_GITHUB_FIXTURE=review /Applications/GitTurtle.app/Contents/MacOS/gitturtle /absolute/path/to/disposable-worktree
```

This is a fixed built-in fixture for `gitturtle-fixture/native-review`, visibly identified throughout the panel. It contains a multi-hunk Rust change, a multilingual renamed Markdown path, a binary file, an incomplete patch, and six conversations across two pages: current, outdated, missing opening context, resolved, paginated, and permission-refused. The longer conversation initially exposes 20 of 23 comments. Replies and resolve/reopen mutations update a shared in-process fixture session and appear after explicit thread/conversation refresh. Restarting resets simulated remote state; local draft/attempt stores retain their ordinary behavior. **Move fixture head** changes the simulated provider identity while retaining the displayed capture; it allows native stale-submission refusal and old-head recovery checks. **Send to offline fixture** exercises the ordinary captured-review and conversation validation and durable attempt recording against this transport.

The fixture transport has no credential, process, or network path. Connect, Disconnect, and PR creation are disabled; unsupported destinations/actions fail locally without fallback. Fixture mode is not a saved account choice and must be supplied again on restart. Drafts and attempt records use their ordinary bounded app-data stores under this distinct fixture identity, so native QA must back up and restore genuine application state. Synthetic success is evidence of native/model wiring only, never a real GitHub write or account authorization.

Hosted validation needs one explicitly authorized disposable GitHub.com repository and account. Its fixture should permit creating/pushing only clearly named fixture branches, creating draft/ready PRs, posting a discussion comment, replying to conversations, resolving/reopening them, and submitting Comment/Approve/Request changes where the account is eligible. A second reviewer account may be needed because authors cannot approve their own PRs. Record the exact account, repository, created object URLs, exercised binary identity, rate-limit/authorization outcomes where feasible, and the user’s retention/cleanup choice. Native and live evidence belongs in the validation record; hosted CI URLs/results are separate.

## Research basis

The API behavior follows GitHub’s [pull-request endpoints](https://docs.github.com/en/rest/pulls/pulls), [review endpoints](https://docs.github.com/en/rest/pulls/reviews), and [rate-limit guidance](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api). The interaction research used GitKraken’s first-party [pull-request workflow](https://help.gitkraken.com/gitkraken-desktop/pull-requests/) and [Launchpad overview](https://help.gitkraken.com/gitkraken-desktop/gitkraken-launchpad/) for explicit creation, visible repository/branch context, and adjacent review/check information. GitTurtle implements those interactions as its own bounded native dialog and existing local comparison flow.

Authoritative conversations follow GitHub's [PullRequestReviewThread object](https://docs.github.com/en/graphql/reference/pulls#pullrequestreviewthread), [reply mutation](https://docs.github.com/en/graphql/reference/pulls#addpullrequestreviewthreadreply), [resolve mutation](https://docs.github.com/en/graphql/reference/pulls#resolvereviewthread), and [reopen mutation](https://docs.github.com/en/graphql/reference/pulls#unresolvereviewthread). Cursor handling follows the [GraphQL pagination guide](https://docs.github.com/en/graphql/guides/using-pagination-in-the-graphql-api); HTTP-200 error handling follows [GraphQL rate-limit guidance](https://docs.github.com/en/graphql/overview/rate-limits-and-query-limits-for-the-graphql-api#exceeding-the-rate-limit).

The application regression `github_view::tests::opening_github_from_an_active_repository_update_defers_local_reads` opens the actual panel/root through the same parent-entity update boundary used by command-palette activation, using a disposable local repository and no account connection or hosted action. It enables GPUI’s supported real-I/O test mode and awaits both serial-executor barriers before teardown, keeping background replies within the test lifetime. Native command-palette and Back/Escape behavior remain package validation checks.
