# GitHub collaboration

GitTurtle’s repository-header **Pull requests** control and **GitHub pull requests…** command open a native panel for the selected local worktree. Overview, Files, and Review keep the captured PR context, conversations, and collected feedback together. Opening the panel reads local remotes and saved drafts only. The initial read is deferred until GPUI finishes the parent view update, so command-palette activation cannot recursively borrow the repository view; a panel closed before that callback skips the read. An interrupted initial local read resumes on warm reopen without replacing edited destination or draft fields. Connect, Refresh PRs, selecting a PR, refreshing or paging conversations, reviewing a new PR destination, and Send to GitHub are explicit network interactions. Opening a reply composer, restoring text, local filesystem refresh, and repository focus do not contact GitHub.

A create form with an invalid destination reports the required `owner/repository` format. Title and body edits remain in the open form, and its status explicitly says the draft is not saved until the destination is valid. Correcting that field queues the retained text for local saving; clicking New pull request again preserves an already open create form. A delayed save reply cannot mark the current invalid destination as saved. Missing PR selection is reported separately from destination validation.

The current provider is GitHub.com. Ordinary Git authentication, profiles, branch Push, hooks, filters, and signing retain their existing paths. PR creation requires an already published branch and never pushes it implicitly.

## Account connection

GitTurtle uses the supported [GitHub CLI browser authentication flow](https://cli.github.com/manual/gh_auth_login), followed by an explicit **Connect GitHub CLI account** handoff. **Copy sign-in command** provides `gh auth login --hostname github.com --web --skip-ssh-key` for a user-driven Terminal sign-in. Keep existing Git choices when the CLI asks about Git configuration; GitTurtle does not invoke `auth setup-git`, upload SSH keys, switch the CLI account, or request credentials in conversation. The installed CLI must be available at `/opt/homebrew/bin/gh` (macOS only), `/usr/local/bin/gh`, or `/usr/bin/gh`; the first that exists is used (`github::transport::GH_CANDIDATES`). The panel's connection pane, which **Account options** opens, names the local worktree above this help on one line: a path longer than the line is elided in its middle, keeping its top directory and its last component as the window header's path does ("Local worktree: /home/…/project"), with the whole path in the line's tooltip and accessible name (`github_view::PathLine`). The pane is a keyboard stop of its own, before its controls, and draws its ring on its edge as the Conversations pane does: Tab or Shift+Tab onto it shows the pane from its top, its worktree line and this help with it, which the stops of its controls alone left out of view in a short window (at 18 pt in a 461 × 490 half tile on macOS, and from 470 to 495 px wide on Linux, no stop showed the worktree line or the help's first line). Every piece of information the panel shows is reachable by keyboard, through the reveal of a stop beside it where that can show it whole, and otherwise as a group stop of its own revealed from its top, as this pane is (owner rule): a PR's captured identities in Overview, its base and head commits, belong to the last section tab, and Tab onto that tab shows them with it wherever both fit the body; where they cannot, as at 17 pt in a window under about 430 px tall, the identities become a group stop after the tab, their ring on their edge, and Tab onto them shows them from their top (`github_view::review::Owned`); only there does a click focus them, so a click never leaves focus on a block no Tab reaches. A pane that holds focus, itself as a click inside one leaves it or on a control inside it as Tab from there leaves it, hands that focus on as it goes: to the control whose press took it away (**Account options** closing this pane, **New pull request** replacing a PR, a Files mode replacing Threads, or a page of files loading), or to the content the panel shows where the page loaded leaves that control disabled; left on a pane no frame drew, focus started the next Tab from the window's first stop (`github_view::Panel::hand_off_lost_pane_focus`). A focused control inside a pane that is still drawn can go too, as **Next comment page** does once the last page has loaded: no press took a pane away, so focus moves to the section shown, the Conversations pane in Overview and the file list in Files (`github_view::review::Panel::focus_visible_section`).

Connect reads the CLI’s current GitHub.com token through a bounded pipe, verifies the account with `/user`, and stores a separate credential in macOS Keychain under service `com.gitturtle.github.oauth`, or on Linux in the desktop keyring ([below](#linux-desktop-keyring)). GitTurtle never enables the CLI’s insecure-storage option and never writes tokens to ordinary preferences, Git profiles, drafts, arguments, or diagnostics. Runtime API processes receive the token only in their transient environment. Stored credential reads temporarily disable interactive legacy-Keychain access and fail with connection guidance if permission is needed. A process-wide try-lock serializes GitTurtle credential calls across windows, preserving the prior interaction policy and refusing concurrent access instead of waiting on another window’s prompt. Explicit Connect/save and Disconnect retain normal macOS authorization. Connect reads the saved account and token back with normal authorization and again with dialogs disabled before reporting success; a successful update alone does not establish readable storage, and one-time permission can still refuse subsequent stored reads. GitTurtle does not modify Keychain ACLs. Connect's success names the store from one place (`github::transport::SecureStore::NAME`): “macOS Keychain” only on a Mac, “your desktop keyring” on Linux and “secure storage” elsewhere, where it once named macOS Keychain on every platform (`github_view::tests::the_panel_says_what_its_cancel_and_connect_did`). The connection pane's help says what Connect does from the store's capability (`SecureStore::HOLDS`), as a stopped Connect's notice does: on a Mac and on Linux, that Connect saves the authorization in macOS Keychain or in your desktop keyring, and that a stopped Connect may already have stored it, which Disconnect removes; on any other platform, where the store saves none, that GitTurtle stores no authorization there, so Connect cannot finish (`github_view::tests::the_connection_help_says_what_connect_keeps`). On Linux no text the panel shows or names for assistive technology says Keychain, encrypted or secure storage (`github_view::tests::the_account_pane_names_only_the_desktop_keyring`). Stored reads never show a dialog or prompt on either platform. Explicit Connect and Disconnect may: macOS shows its own authorization dialog, and on Linux the desktop keyring shows its own prompt to create, unlock or confirm. Late connection cancellation reports that authorization may remain stored. Disconnect removes only GitTurtle’s own item, the Keychain item or the desktop keyring's; it does not revoke the account or log out the CLI. Disconnect passes its request's own Cancel to the store, so on Linux Cancel reaches the keyring's prompt (`github_view::tests::disconnect_reaches_the_account_with_its_own_cancel`). Cancelled before the removal begins, as while a background read still holds the executor ahead of it, such as a quiet refresh's status read or the panel's own local read of remotes and drafts (another write or request is refused before Disconnect is sent, so none can be ahead of it), Disconnect keeps the item and says “Cancelled · GitTurtle's authorization was kept” in the failure's place, as a cancelled comparison says it was cancelled, where it once removed it after Cancel and then showed the kept item as a failure; Connect cancelled before it reads the CLI's token says “Cancelled · no account was connected”, or, with an account already connected, which it leaves as it was, “Cancelled · the account is unchanged”, where it once said no account was connected while the toolbar named one (`github_view::tests::a_cancelled_connect_says_what_it_left_of_the_account`). Test builds reach a stand-in for the CLI and the store (`github_view::account`), so no test starts the CLI, reads a developer's token or removes their stored authorization, even where that guard regressed (`github_view::tests::connect_and_disconnect_name_themselves_from_their_buttons`). The guarantee is structural: a test build has no store at all (`github::transport::CredentialStore` with its reads, saves and removals, `GhTransport::stored` and `GhTransport::connect_existing` are not built for tests), so a test that calls one fails to compile, and a transport opened with the fixture off refuses there before any store, where a test's Refresh PRs with the fixture off would have read the stored authorization (`github::review::tests::a_test_build_opens_no_live_transport`).

API subprocesses use an absolute `https://api.github.com/` destination and a fresh private, empty `GH_CONFIG_DIR`, removed after the process finishes. CLI `api_host` and `http_unix_socket` configuration cannot reroute GitTurtle's credential. The explicit CLI token handoff retains the user's CLI configuration; ordinary Git authentication and system HTTPS proxy/TLS configuration retain their existing behavior. HTTP redirects remain governed by the installed CLI and its HTTP library, so fixing the initial origin is not an application-owned redirect allowlist.

The credential store is a platform abstraction with no file fallback: on a platform other than macOS and Linux, connection refuses persistence instead of writing a plaintext file. CLI OAuth itself, actual Keychain unlock, the desktop keyring's own prompts and hosted account authorization require separate environment-dependent validation.

### Linux desktop keyring

On Linux the store is the desktop keyring (gnome-keyring on Omarchy; other Secret Service providers such as KWallet and KeePassXC have not been checked), reached through the freedesktop Secret Service with oo7's D-Bus client (`github::transport::secret_service`; [research and decision](development/2026-10-28-linux-github-secret-service.md)). GitTurtle keeps one item in the collection behind the `default` alias, “Default keyring” on Omarchy and “Login” on GNOME, and never uses the `session` collection:

| Field | Value |
| --- | --- |
| Collection | the `default` alias |
| `xdg:schema` | `com.gitturtle.github.oauth` |
| `service` | `com.gitturtle.github.oauth` (the macOS item's service) |
| `username` | `github.com` (the macOS item's account) |
| Label | `GitTurtle GitHub authorization (github.com)` |
| Secret | the macOS item's JSON `{login, token}`, `text/plain` |

Every search and the one write use all three attributes, so another application's item with the same `service` and `username` is never read as GitTurtle's.

- **Prompts only on Connect and Disconnect.** A stored read (Refresh PRs, opening a pull request) never asks the keyring to unlock or create anything. A missing `default` alias or item is no stored account; a locked keyring, a keyring service that does not answer, an entry that is not the account's JSON, or more than one GitTurtle entry is an error that says what to do. **Connect GitHub CLI account** may show the keyring's own prompt to create or unlock the default keyring, and **Disconnect GitTurtle** one to unlock it or confirm a removal.
- **Read back after save.** Connect writes the item, replacing any earlier one, then reads it back without any prompt, as Refresh will, and compares the account and token before it reports success.
- **Disconnect searches only the default keyring.** It removes every GitTurtle item from your default keyring and checks that none remains. If you changed which keyring is the default since Connect, the item stays in the old one, where Seahorse shows it.
- **Bounds.** A stored read ends within 5 seconds. Connect and Disconnect end within 2 minutes or within 100 ms of Cancel, saying when the write or removal had already gone out, so the authorization may remain stored. One keyring call runs at a time across windows; a second is refused at once rather than opening a second prompt. Each call opens one fresh connection, which survives a restarted keyring daemon, and runs on the window's operation executor, never the UI thread.
- **Every failure fails closed.** GitTurtle writes no credential file and has no other fallback, and no message carries the token or the keyring's own error text (`secret_service::tests::an_accounts_life_in_the_keyring_shows_its_token_nowhere`).
- **Never called encrypted.** The interface says the authorization is stored in your desktop keyring. A keyring without a password, Omarchy's default, is kept unencrypted on disk by gnome-keyring, and GitTurtle cannot tell through the Secret Service; the [Linux limits](linux.md#platform-limits) say how to set a password.

The flows run against a fake keyring in every Linux test run (`secret_service::tests`). The opt-in hermetic test runs the real client against a disposable gnome-keyring on a private D-Bus that it starts and stops itself, never the developer's session bus: save, read, replace, remove, duplicate and invalid entries, a locked keyring refused well within the read bound without an unlock, and a bus with no keyring (`secret_service::tests::hermetic`; the commands for it and for the release measurement of a stored read are in its doc comments). It needs `dbus-daemon` and `gnome-keyring-daemon`, which the hosted Linux jobs do not install.

Selecting a PR loads current title, exact description source, draft/open state, head/base branches and complete commit identities. The explicit selection separately loads review history, check runs, commit statuses, the first changed-file page, and the first authoritative conversation page. Each status endpoint is bounded to 100 entries; additional entries or partial endpoint failures are explicitly reported. Older-head reviews are identified. These entries report provider results and do not infer an aggregate approval decision or merge authorization.

New PRs support title, exact description text, Draft or Ready, destination base, and a published head. An `owner:branch` head resolves the same repository name under the named owner. Creating from a differently named fork repository is outside the current form. **Review outbound action…** resolves the published branch identities and shows them with the account and destination. **Send to GitHub** rechecks those identities, refuses moved branches, and makes one create request. The REST create endpoint accepts branch names rather than a conditional head SHA, so the small interval between the final check and provider acceptance is not an atomic ref lock.

**Load local base templates** reads supported Markdown template paths from the selected locally available base revision: `pull_request_template.md` in the root, `docs`, or `.github`, and Markdown files immediately inside the corresponding `PULL_REQUEST_TEMPLATE` directory. Matching is case-insensitive. The selected source revision is shown, regular Git blobs are used, symlinks are ignored, and working-file edits cannot change the captured template. Up to 32 templates and 256 KiB per template are supported. Choosing a template appends its exact text. A missing local base asks for an explicit Git fetch or a locally available base name; it never downloads objects automatically. ## Comments, reviews, and local recovery

The native Review section supports discussion-only comments and collected reviews with Comment, Approve, or Request changes. Approval and change-request permissions remain GitHub’s decision. Comment reviews can collect inline feedback without a summary; Request changes requires a summary. Every submit confirmation shows the account, repository, PR number, full head/base identities, event, summary, and every inline comment with its captured path and position. The service rereads the PR before posting and refuses moved head/base identities or a closed PR. Reviews include the captured `commit_id`; if a head moves after the check, the review remains associated with the reviewed commit. Positions are never silently remapped.

**Files** provides a native changed-file list, a virtualized unified patch, exact patch Source, and file-specific Threads. Explicit pages contain up to 100 files, within GitHub’s 3,000-file endpoint limit. File pages replace the visible page. Metadata retains bounded raw patches; only an explicit file selection, or its resumption on reopen, prepares line rows on the worker, which shares the selected patch with the view rather than copying it on the UI thread. Switching files, replacing a page, or closing cancels replaceable preparation, and generation checks reject late results. Each page is bracketed by captured-head/base checks; a moved identity refuses the result. These reads use provider-supplied patches and do not fetch Git objects or require a local checkout of the PR branch. **Open captured local comparison** remains available for locally present text, images, documents, and other supported content.

Click a changed line, or use Up/Down in the patch list. Shift-click or Shift-Up/Down extends a range; Return or **Comment on selection** opens the inline composer. Supported ranges contain consecutive added lines or consecutive deleted lines on one side of one hunk. Cross-side selections, context-only selections, hunk boundaries, malformed/truncated patches, and unavailable binary patches cannot become inline positions. Parsing verifies hunk counts and the reported total additions/deletions, with a 20,000-row inline limit. Source preserves the exact supplied patch, including when inline anchoring is refused. **Add to review** collects a comment locally. Review shows all collected positions and text, with Edit and Remove actions. A separate unfinished composer is also saved; submission asks the user to add or discard it. File and section navigation keep that composer attached to its original captured position. Collected reviews support at most 100 inline comments and use optional `start_line`/`start_side` for ranges. Discussion-only posting is disabled while inline feedback is present, avoiding an accidental submission that omits it.

Overview and file-specific Threads use GitHub GraphQL `PullRequestReviewThread` identities, resolution state, outdated state, and viewer permissions. Resolved/unresolved labels come from the provider; REST comment grouping never establishes conversation state. Each explicit page requests at most 25 conversations with 20 comments per conversation. **Next comment page** requests at most 100 comments for one captured thread and replaces its visible comments; **Refresh thread** returns to its opening page. The opening comment is requested separately on every thread read, preserving its identity even when the displayed comments are a later page. Conversation pages replace the visible list, retain bounded Previous/Next cursor navigation, and stop at 1,000 pages per inspection. Opaque cursors are limited to 1,024 bytes; missing, repeated, empty, or inconsistent continuation metadata is refused with explicit refresh guidance.

Outdated conversations retain their original commit and Before/After positions, including supplied range sides, independently of the current PR head. A deleted author is labeled Deleted account. A missing opening comment or nullable comment node leaves available text readable and identifies incomplete context; replying remains disabled. A missing conversation node, malformed response, or GraphQL error refuses that response rather than presenting a partial page as complete. File-specific Threads reports only conversations on the loaded page, so an empty file view does not assert that no conversations exist elsewhere.

The panel's own Cancel says what it asked for in the request's words (`github_view::RequestKind::requested`): that a read changes nothing and keeps the drafts, that a sent action may already have been applied, that Connect's authorization may already be stored where the platform's store can hold it, on a Mac, and elsewhere that GitTurtle stores none there (both it and the bar's tooltip worded from `github::transport::SecureStore::HOLDS`, where Linux once said the authorization may already be stored), that Disconnect keeps the authorization unless its removal has begun, or that a local comparison or templates read changes nothing; it once said “Your review draft is retained” during Connect, Disconnect and a comparison, which involve no review draft. The spell lasts until the executor answers even once the panel has closed, as closing during a read does. While a Git write runs, the panel sends nothing and says why, and a confirmed action it refuses keeps its confirmation, so Send sends it once the write ends; the refusal once dropped the confirmation, and the submission had to be reviewed again (`github_view::tests::a_confirmation_a_git_write_refuses_stays_to_send`). The panel's local read of remotes, drafts and attempts as it opens stays a passive read on that executor, bounded and local like the status read itself, with no busy spell. Before sending, it records a pending attempt in the independent `github-attempts.json` file, then records the observed result. This file retains the latest attempt per captured destination/account, bounded to 128 destinations and 1 MiB. An interrupted process can leave a pending record, which the next panel opening shows. Accepted actions are never automatically replayed. The active panel keeps its captured destination visible and requires the action to finish, or explicit cancellation to finish, before closing normally.

A confirmed reply outcome also records a SHA-256 receipt of its exact captured identity and body in the bounded attempt record. Recovery checks these receipts before restoring text, so failure of draft-cleanup saves cannot revive known completed replies as unfinished, including when another reply succeeds while saves still fail. Pending, failed, and resolve/reopen attempts retain earlier receipts; later confirmed replies append distinct receipts. The store preserves up to 128 receipts per destination within its 1 MiB total allowance, accepts legacy single-receipt entries, and refuses overflow without dropping proof. An attempt carrying receipts is never evicted to make room for another destination; only entries without receipts follow the existing destination-eviction policy. No receipt is retired without proof of durable cleanup, and the current implementation conservatively retains them. A full protected store refuses a new pending attempt before dispatch; failure to record an additional successful outcome requires explicit verification against GitHub.

Successful reply cleanup queues an empty snapshot through the same draft saver as typing and removes only that captured reply entry. It cannot overtake an earlier accepted save or clear newer text. Empty replies release draft capacity before other identities in the same atomic batch are added. Receipts do not duplicate reply bodies or credentials.

Draft and attempt reads use the shared descriptor-based bounded app-data reader. A coalesced draft batch merges all pending identities before one atomic replacement; an entry or byte overflow preserves the previous complete store. Attempt writes check the encoded JSON byte limit, including escaped text, before replacement. A pending-record save failure prevents dispatch, and an outcome-record save failure preserves the earlier pending record and requires explicit verification of the remote outcome.

Cancellation, transport deadlines, lost responses, server failures, and invalid success responses may leave an uncertain remote outcome. The panel preserves text and asks the user to inspect GitHub before submitting again. A success response followed by a local outcome-save failure also requires verification rather than replay. Authentication expiry, permission refusal, validation failure, and rate limits have distinct guidance. Rate-limit reset and retry-after headers are reported without automatic retry. A retry-after header's wait keeps its unit: whole seconds agree with their noun ("Retry after 1 second.", "Retry after 30 seconds."), a decimal number of them reads as seconds too, written as a number is ("Retry after 1.5 seconds.", where it once lost the unit as "Retry after 1.5."; "5." as "5 seconds", ".5" as "0.5 seconds"), whole seconds beyond what the app counts in stay seconds, and an HTTP date is given as the header gives it, a date and a time, rather than converted on a clock the header's sender does not share (`github::retry_after`).

## Bounds and evidence

Requests use the [GitHub CLI API interface](https://cli.github.com/manual/gh_api), fixed GitHub.com routing, REST version `2026-03-10`, and fixed GraphQL queries/mutations with separately supplied variables. Network work stays on the operation thread. Subprocess I/O is nonblocking and drained under a 90-second API deadline (30 seconds for token handoff), an 8 MiB response limit, and 64 KiB diagnostic/header limits. Explicit cancellation kills and reaps the process group. Diagnostics are discarded rather than displaying potentially sensitive CLI output. GraphQL errors are checked even under HTTP 200; permission, authorization, and rate-limit guidance does not schedule a retry.

`cargo test --locked -p gitturtle github` exercises changed-line/range selection and refusal, incomplete and absent patches, renamed paths, fixture isolation, legacy single-line decoding, inline-only collected reviews, mid-read head movement, unfinished/invalid submission refusal, complete draft roundtrips, actual GPUI Return/range composition, warm reopening across an interrupted local read, template-driven cache eviction, minimum-window composer visibility, rapid file replacement and destination-change flushing, and the existing repository/URL validation, pagination without following foreign links, moved-head review refusal, moved-base create refusal, captured review commit/side/line, draft/ready creation fields, cancellation before dispatch, cancellation of a live subprocess, request-body EOF, bounded output, rate limits, expired authorization, no replay after a simulated lost write response, exact draft recovery, and preservation of an invalid draft store. These are fixture and local-process tests; they are not evidence of a real GitHub write, Keychain access, a desktop keyring other than the hermetic test's disposable one, native VoiceOver use, or hosted CI.

Conversation regressions cover authoritative resolved state, exact root/node/account identities, current and outdated positions, permission refusal, independent comment pagination, missing/partial context, malformed and uncertain mutation responses, cursor refusal, and cancellation without replay. Draft regressions preserve all captured identity fields and exact Unicode/whitespace, distinguish changed targets and separator-containing paths, retain previous stores after failed batches, serialize completion behind an in-flight text save, and suppress a completed reply after cleanup failure. The native fixture's model tests exercise reply → explicit refresh → resolve → refresh → reopen against its stateful provider. ## Research basis

The API behavior follows GitHub’s [pull-request endpoints](https://docs.github.com/en/rest/pulls/pulls), [review endpoints](https://docs.github.com/en/rest/pulls/reviews), and [rate-limit guidance](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api). GitTurtle implements those interactions as its own bounded native dialog and existing local comparison flow.

The application regression `github_view::tests::opening_github_from_an_active_repository_update_defers_local_reads` opens the actual panel/root through the same parent-entity update boundary used by command-palette activation, using a disposable local repository and no account connection or hosted action.
