# CI observations — September 16, 2026

Hosted evidence for the Rust dependency cache after the capacity repair
([PR #14](https://github.com/FernandoX7/GitTurtle/pull/14), main `c66aef5`).
**The first trusted-main run after the repair saved all four compiled seeds, and
the first controlled warm PR run reached the Quality gate 7m39s after creation,
against 20m33s cold.** Each figure below is one observation; none establishes a
distribution or tail latency. The September 15 record is
[2026-09-15-ci.md](2026-09-15-ci.md).

## Measurement boundary

Elapsed means workflow creation to the last job completion. Execution span means
first job start to last job completion. Runner time sums non-skipped job
intervals, including overlap. Restore duration is the pinned action's own
log-marker interval, not the enclosing setup step; the helper's
`rust-cache-restore.json` interval additionally includes dispatch and recovery.
Budget work is the helper's recorded `elapsed_seconds`. Compressed sizes are the cache service's `size_in_bytes`. Cold
references come from the PR run at `6387aad` on the day's runner images.

## Warm main push at `a3c57ab`

[Quality 35103777760](https://github.com/FernandoX7/GitTurtle/actions/runs/35103777760)
(push to `main` after fork PR #15 merged; product Rust sources and docs only,
no cache input changed) passed all 12 jobs in **489s** elapsed against 1238s for
the cold seed run, runner time 1924s against 3958s. All four restores were
exact-key hits (16.5s, 25.3s, 19.0s and 23.6s for the Linux debug, macOS debug,
Linux release and macOS release lanes). Every budget record again reported
`save=true` with zero evictions (helper 6.2s to 22.3s), the registration step
found each key already present, and upstream's post action logged only
`Cache up-to-date.`: no upload, no new entry, and the four archives kept their
identity. Test counts rose to 804 (Linux) and 798 (macOS) with the merged
change. In this observation the save side of a main push cost one lookup-only
check per lane (0.9s to 2.5s) because every key already existed; a new upload is
expected only when a cache input changes the key.
