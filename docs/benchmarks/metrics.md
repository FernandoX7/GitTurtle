# Trace metrics and harness boundaries

`gitturtle.commit_files_frame_ms` measures selection handling through the changed-file-list frame callback; `gitturtle.file_preview_frame_ms` measures history-file activation through the prepared-preview callback. `gitturtle.working_preview_frame_ms` measures working-file activation through that callback, not the preceding status refresh or Git write. `gitturtle.history_page_frame_ms` measures the ordinary page handler through its next frame callback. These exclude pre-handler input delivery, OS presentation, and completed GPU execution. The status bar's content-read duration is worker work only. Historical `selection_frame_ms` includes eager previews and is not directly comparable. Save new records under `docs/benchmarks/` without rewriting previous measurements or attributing them to newer builds.

This catalog is a documentation path tasks may extend: when a task adds a new `GITTURTLE_TRACE` measurement, add the metric's exact name, its start/end boundary and what it excludes here, in the same style as the existing entries.

`gitturtle.theme_apply_frame_ms` measures a built-in theme switch from entry to the Settings `choose_theme` handler through the window's next frame callback. It prints once for each switch that changes the selection; reselecting the current theme prints nothing, and follow-system toggles and custom-theme selection are not traced. It includes `apply_appearance` (theme tokens, text sizes and in-place restyling of retained patch, split, file-history and revision editors), submitting the preference save to its executor, and the wait until the platform requests the next frame. Like the other `*_frame_ms` metrics it ends at the next-frame callback, which GPUI 0.3.4 runs before it lays out and paints that frame, so it excludes the layout and paint that show the new theme, pre-handler input delivery, the preference write (serialized off the UI thread), OS presentation and completed GPU execution. The wait for the frame request follows the display's refresh cadence and dominated the value on the Linux X11 baseline host, so compare distributions only at the same refresh rate. The [themes specification](../development/themes/spec.md#performance) defines its fixture and budget; the first release baseline, measured on build `7924244`, is [2026-09-18-theme-apply.md](2026-09-18-theme-apply.md). A theme switch submits no worker job and keeps retained editors and Find state (`settings::theme_apply_tests`). The custom theme editor prints the same name once per open and once per burst of live-preview edits (`theme_editor::preview_theme_draft`), with its own edit boundary: from the edit handler through the frame that shows the draft. The stamp is taken in the edit handler, where the first draft of a frame applies; the next frame callback applies any draft coalesced from later edits in that frame and registers a second callback; that frame then lays out and paints the draft; and the line prints at the second callback. Unlike a switch, an edit value therefore includes the layout and paint of the frame that shows the draft, plus the refresh wait before the following frame request, and it still excludes pre-handler input delivery, OS presentation and completed GPU execution. Compare editor values only with editor values: the ten-edit release record is kept separately from the switch baseline, and by the [owner decision](../development/themes/spec.md#performance) of 2026-09-19 the 16 ms p95 edit budget is owned by `themes-draw-cost`, not by the editor.
