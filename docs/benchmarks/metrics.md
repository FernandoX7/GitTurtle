# Trace metrics and harness boundaries

`gitturtle.commit_files_frame_ms` measures selection handling through the changed-file-list frame callback; `gitturtle.file_preview_frame_ms` measures history-file activation through the prepared-preview callback. `gitturtle.working_preview_frame_ms` measures working-file activation through that callback, not the preceding status refresh or Git write. `gitturtle.history_page_frame_ms` measures the ordinary page handler through its next frame callback. These exclude pre-handler input delivery, OS presentation, and completed GPU execution. The status bar's content-read duration is worker work only. Historical `selection_frame_ms` includes eager previews and is not directly comparable. Save new records under `docs/benchmarks/` without rewriting previous measurements or attributing them to newer builds.

This catalog is a documentation path tasks may extend: when a task adds a new `GITTURTLE_TRACE` measurement, add the metric's exact name, its start/end boundary and what it excludes here, in the same style as the existing entries.

`gitturtle.theme_apply_frame_ms` measures a theme switch, to a built-in or to a saved custom theme, from entry to the Settings `choose_theme` handler through the window's next frame callback. It prints once for each switch that changes the selection; reselecting the current theme prints nothing, and follow-system toggles are not traced. It includes `apply_appearance` (theme tokens, text sizes and in-place restyling of retained patch, split, file-history and revision editors), submitting the preference save to its executor, and the wait until the platform requests the next frame. Like the other `*_frame_ms` metrics it ends at the next-frame callback, which GPUI 0.3.4 runs before it lays out and paints that frame, so it excludes the layout and paint that show the new theme, pre-handler input delivery, the preference write (serialized off the UI thread), OS presentation and completed GPU execution. The wait for the frame request follows the display's refresh cadence and dominated the value on the Linux X11 baseline host, so compare distributions only at the same refresh rate. The [themes specification](../development/themes/spec.md#performance) defines its fixture and budget; the first release baseline, measured on build `7924244`, is [2026-09-18-theme-apply.md](2026-09-18-theme-apply.md). Choosing the Linux Omarchy card applies nothing in the handler: since 2026-09-28 it starts a read of the desktop's current theme and applies when that read lands, or the cached palette after 100 ms, so for that card the metric runs from the handler's entry through the next frame callback after that application and includes the wait for the read (the read itself, `omarchy_reread_ms`, plus the hop back to the UI thread; at most the 100 ms wait). When a slower read then changes the palette again, that second application prints `omarchy_apply_frame_ms`. A theme switch submits no worker job and keeps retained editors and Find state (`settings::theme_apply_tests`). The custom theme editor's opens and edits do not print this metric; they have their own.

`gitturtle.omarchy_reread_ms` and `gitturtle.omarchy_apply_frame_ms` measure the Omarchy theme on Linux ([themes specification](../development/themes/spec.md#omarchy-theme)). `omarchy_reread_ms` prints once per reread of `~/.local/state/omarchy/current/`, on the background executor: reading `theme.name` and `colors.toml`, parsing, mapping and fitting the palette, and its readability check, excluding the 250 ms quiet period a watched switch waits first and the hop back to the UI thread. `omarchy_apply_frame_ms` prints when a reread changes the palette of a selected Omarchy theme, other than the read a choice of the card waits for, which `theme_apply_frame_ms` covers. It runs from the result's arrival on the UI thread through `apply_appearance` to the window's next frame callback, following the pattern of `theme_apply_frame_ms` and with the same exclusions: the layout and paint of that frame, presentation, and the wait for the platform's frame tick, which varies with the display's refresh rate. A reread that finds the same palette prints the reread and no apply. Neither has a recorded release baseline yet.

`gitturtle.theme_edit_frame_ms` measures a custom theme editor open or a burst of live-preview edits through the draw of the frame that shows the draft. It prints once per open and once per burst of edits between two draws; an invalid value applies no draft and prints nothing. The stamp is taken at entry to the token row's change handler (the hex `Input`'s `InputEvent::Change` or the `ColorPicker`'s change, before the value is parsed; an open stamps at `open_theme_editor` entry) and is kept by `theme_editor::State` until the root render takes it (`GitTurtle::edit_trace_probe`) into a zero-size element deferred at a priority above the dialog layer, so that it is the last element `Window::draw` paints in the first frame drawn after the handler applied the draft, whether that draw runs in the frame tick or synchronously in `Window::dispatch_key_event`; the line prints from that element's paint. It therefore contains the parse, the readability recompute, `apply_appearance` and the request_layout, layout, prepaint and paint of the whole window with the dialog over it, and excludes next-frame callback waits, frame-finish bookkeeping, present, pre-handler input delivery and completed GPU execution. The frame-tick grid does not enter the value, so it is comparable across refresh rates. `theme_editor::tests::an_edit_trace_ends_in_that_frames_paint_after_the_dialog` asserts one probe paint per edit, ended in that edit's single draw after the dialog painted and never from a next-frame callback. The [themes specification](../development/themes/spec.md#performance) defines its fixture and the 24 ms p95 budget over 60 pooled edits; the diagnosis that re-cut the boundary is [2026-09-19-theme-editor.md](2026-09-19-theme-editor.md).
