# Performance measurement

Use this reference when collecting or assessing latency or memory evidence. Choose the harness for the affected layer; a backend or graph-only result does not establish native interaction speed.

For performance claims, use release builds and repeatable navigation over the same immutable commit/file data. For Working Changes, record reproducible HEAD/index/worktree fixture state, staged or unstaged area, activation sequence, and any writes between samples. Record build revision, hardware, sample count, raw samples, median/tail/max, other load, and application versus filesystem cache conditions. Retain outliers; missing or superseded samples are not zero latency. Inspect resource growth under rapid selection when the change affects allocation or cancellation.

Use the exercised executable's `--build-info` or About/Copy bug diagnostics to identify its compiled revision, tree state, target and profile. For a modified tree, retain the tested source delta or compiled-input manifest; the revision alone is incomplete provenance. Package metadata and the present checkout can differ from the executable. Record window/tab counts when interpreting memory or concurrency because the [worker ownership scopes](../../../../crates/app/docs/navigation-and-refresh.md#worker-and-observer-ownership) differ.

See [Trace metrics and harness boundaries](../../../../docs/benchmarks/metrics.md) for the frame-trace metric names, their exact boundaries, and the per-path harness table.

For status, working-preview, search, file-history, or changed-file backend measurements, use the existing [everyday benchmark procedure](../../../../docs/benchmarks/everyday-bench.md) and `gitturtle-core`'s `everyday_bench` example. Its release samples include core work only; they exclude app scheduling, prepared UI presentation, image decoding, writes, and native frames. Inspect raw attempts, result fingerprints, skipped areas, and continuation limits before making a comparison. Existing frame traces do not establish search, attribution, or watcher end-to-end latency; instrument the affected boundary when a claim needs that evidence.

For a graph-only comparison, [bench-graph-layout.py](../../../../scripts/bench-graph-layout.py) extracts the layout and compiles an optimized standalone harness, with an optional explicit baseline revision. Its in-memory samples exclude Git, budget preflight, GPUI, and native navigation; report them as algorithm-only evidence, separate from application frame measurements. A graph-only benchmark does not require rebuilding the native app.

Other existing harnesses cover the newer paths. Inspect their options and source identity before reuse; select only the relevant layer.

For image cleanup, `GITTURTLE_TRACE` emits registration and retirement events from [image_lifetime.rs](../../../../crates/app/src/image_lifetime.rs), including retired frame counts and retained images after closure. Pair repeated open/Back/tab/close cycles with process observations. Retirement events establish app calls to `App::drop_image`, not Metal allocation bytes; report retained tab/document owners and cache conditions before drawing a memory-growth conclusion.

For native scrolling, `GITTURTLE_TRACE_SCROLL=1` enables input/geometry observations in [diff_view.rs](../../../../crates/app/src/diff_view.rs) and [split_diff.rs](../../../../crates/app/src/split_diff.rs). The `split_paint` record observes both panes after painting, including offsets, text bounds and visible rows; `split_link` records a linkage request. Correlate by window/editor identity and use code-area and gutter gestures, reversal and the affected text/display scale. These logs do not request additional frames. They can demonstrate alignment in the observed paints; timestamp gaps or a final equal offset do not establish display frame rate, end-to-end input latency or smoothness. Pair relevant traces with native observations, and preserve the raw records.
