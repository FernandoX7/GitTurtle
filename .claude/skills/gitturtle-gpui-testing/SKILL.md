# GPUI view tests

A UI change is proven by a rendered-node test, not a screenshot. Write `#[gpui::test] fn name(cx: &mut gpui::TestAppContext)`, start a test that builds the app with `views::tests::init_app(cx)` (it runs `gpui::init` and gives every seed empty settings, so nothing one iteration saves reaches the next; a bare `cx.update(gpui::init)` is for views that never build the app), build the view with `cx.add_window_view(|window, cx| ...)`, drive it with `simulate_keystrokes`, `simulate_click` and `simulate_resize`, settle with `run_until_parked`, and assert `debug_bounds`, focus and `accessibility_label` text. Follow the neighboring test module's setup helpers rather than inventing new fixtures; `split_diff.rs`, `scroll_tests.rs` and `repository_tabs.rs` show measured-viewport assertions.

Run the narrowest filter first (`cargo test --locked -p gitturtle <module>::<test>`), then the module, then the fast gate. The harness is deterministic under a seed: reproduce a failure with `SEED=<seed> cargo test --locked -p gitturtle <test> -- --nocapture` using the seed the failure printed, and sweep for flakiness with `ITERATIONS=100 cargo test --locked -p gitturtle <test>`; the vendored runtime (`gpui-pre` 0.3.4, `src/test.rs`) reads both variables, and the macro also accepts `iterations`, `seeds`, `retries` and `on_failure` attribute arguments for a permanent per-test setting. The fast gate reruns changed `#[gpui::test]` functions with `ITERATIONS=20`. Never commit `retries`, which masks failures: a test that only passes with retries has a real scheduling or generation bug.

A repository a test opens gets its own Git identity through `views::tests::fixture_repository` or `fixture_identity`, so the host's global configuration never changes the composer or the layout. Time and background work are controlled: tests must not depend on wall-clock timing (wait for a read by its completion, as `tags::tests::read_lands` does or by draining the operation executor as `focus_ring::sweep::open_dialog` does). Those waits (`SerialExecutor::drain`, `Worker::wait_idle`) fail after 30 s rather than hang; `GITTURTLE_TEST_WAIT_SECS=<seconds>` raises that bound on a slow host and never lowers it. Every spawned read must be settled or cancelled by the test's end so the leak timeout in `.config/nextest.toml` does not report it. A test that waits for a real child process (a stand-in for `fc-match`, a sleeper) holds the test clock while the child starts and lets it move only for that child's finished output (`desktop_text`'s `until_clock_held`): advancing the clock inside a real-time wait spends the product's bound on a slow process start, which only a loaded host shows. Likewise wait for a dialog's motion to end (reduced motion, or a control drawn in the same place in two frames) before clicking it. Theme assertions compare resolved native component backgrounds with foregrounds. Visual correctness of the real window still needs the native-QA evidence rows; say so instead of claiming it from a test.

Three races recur. A test that sets app state a quiet read can replace (the profile, the branch, the Git identity) holds quiet reads first (`views::tests::hold_quiet_reads_for_test`); `width_walk::open` does this for every caller and lands the walk's identity before any page opens, so a late rescan cannot change the header between two passes (FU20-M). A per-thread cache (a `thread_local!` of measured widths or texts) survives from one seed to the next on the same thread, so a test that counts its fills empties it at its start (`views::forget_status_text`), never by putting back a redundant change; the gate's 20 iterations on a small round are what surface it. Test layout uses GPUI's fixed-advance `NoopTextSystem` on every platform, so a test whose geometry differs on the macOS runner is racing, not reading other fonts: find the late read, as FU20-M did.
