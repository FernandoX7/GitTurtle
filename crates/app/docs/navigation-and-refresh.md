# Navigation and refresh contracts

Read this when changing or reviewing page/mode transitions, focus, selection, worker scheduling, search, retained inspections, or local refresh. Source ownership is mapped in [app guidance](../AGENTS.md); the broader flow is in [architecture](../../../docs/architecture.md).

## Selection and asynchronous replies

Commit selection in History requests `Job::Changes`; a highlighted file is not an activation. Explicit activation enters Compare. `receive(Output::Preview)` may retain current content after Back, but cannot reopen Compare or initialize a hidden editor. Preserve generation checks and both the `AppPage::Repository` and workspace-mode guards when changing asynchronous code.

Back from Compare restores the retained scope, query, loaded history, selection, scroll position, and inspector without another Git request. Working Changes keeps history files separately in `retained_history_files`; do not reuse mutable working files as the history inspector. History-changing writes use `refresh_after_write` to queue a quiet refresh, preserving the valid selected scope, pinned query, and immutable comparison. Re-resolve mutable branch/worktree identities; session reuse must not freeze tips. Parent changes keep the displayed comparison and selected file consistent. Rebuild selections from stable commit/file identity rather than virtualized row indices.

Working-status replies check both `work_generation` and canonical repository identity. Refresh and writes use `invalidate_read` to advance the preview generation and cancel obsolete work when mutable content is invalidated, even when the next selection is empty. Retain the user's current path/area at reply time, including movement between staged and unstaged groups; do not restore the selection captured at dispatch. Mutable previews bypass the immutable cache.

## Worker and observer ownership

Bounds apply at each owner's scope, not automatically to the whole process. Trace the owning state and its cancellation/release path before adding background work:

| Work | Current owner and lifetime |
| --- | --- |
| History, selected previews, search and quiet reads | Each window's `GitTurtle::worker`; tabs share that reader and invalidate obsolete work when switching. A History snapshot reads its tags on one scoped thread beside its history page, under the same cancellation, and joins it before returning. |
| Accepted Git writes and preference saves | Separate `SerialExecutor` instances created by each `GitTurtle`; accepted writes drain after a reply is dropped. This is not a process-wide Git transaction lock. |
| Changed/working path filtering | The window's lazy `path_filter::State` executor, with snapshot identity and cancellation tickets; working filtering reuses this lane. |
| Later PDF pages and model frames | Separate process-wide `OnceLock` renderers in `pdf_view::renderer` and `model_view::renderer`; content owners retain their own caches, generations and cancellation. A shared lane does not make retained view memory global or free. |
| Stash inspection | The dialog's `StashBrowser` owns a metadata executor and preview `Worker`; replacement/closure must also pause retained documents. |
| Linux desktop preferences | One app-global `desktop_text::Observer`; see [desktop observers](#desktop-observers). |

New read jobs need a captured identity, a bounded queue/input/result and a terminal path for supersession, error and owner release. Keep accepted writes on their existing path. Do not add a second persistence or Git policy implementation to a native view merely because it uses a separate executor.

## Pages and focus

Projects and Settings are pages separate from the retained repository modes. Construct elements only for the active `AppPage`; calling a hidden page renderer still builds its lists, controls and previews. Keep the root `app_focus`, history `focus`, and `file_focus` handles distinct. Settings focuses its first control (Follow system appearance, or the selected theme's card while the desktop's Omarchy theme makes that switch unavailable) and Projects its selected action tab, both inside the root, so application shortcuts remain reachable and each page opens with its focus drawn; Settings marks that focus on the window's `FocusRing` and reveals it in its page however it was opened, every time it opens (`FocusReveal::reveal_next_focus` reveals even the control the page last drew focused, since the page reopens at its top). Keep `GitTurtleList` navigation out of editable form fields; hidden editors must not steal focus. Retain the selected file's visibility as lists change. Temporary search expansion must not overwrite saved branch-folder expansion choices.

On Linux, use compositor-provided window decorations when available. Otherwise the repository-tab strip supplies accessible window controls on every page, following the desktop's button placement/order and the compositor's supported minimize/maximize actions. Blank header space supports dragging, double-click maximize and the native window menu. Close uses the existing Close Window action and normal shutdown observers and is disabled while a Git operation is running. macOS retains its native title bar, traffic lights and application menu; the primary-modifier Quit shortcut remains available on both platforms.

Folder-picker cancellation retains the current repository and form input. Request failures surface on the current page, with Linux FileChooser service guidance and a command-line path fallback. Linux startup without a graphical session exits with a diagnostic; Git askpass dispatch still happens before this check.

Switching between History, Working Changes and Settings only reads, so a running write leaves it available from every route: the shortcuts, the header's toggles, the palette, both platforms' menus and the empty-state and paused-operation actions that open Changes (`page_navigation::tests::page_switches_stay_available_while_a_write_runs`). No working-state read waits behind a write: while a write or a review's preparation runs on the operation executor, in the shown repository or another tab's, a clone or create included, `refresh_worktree` (which `show_working` calls) only notes the read (`working_read_deferred`), and whatever ends next, write, clone, create or preparation, reads the shown repository's working state (`read_deferred_working`). So does whatever cancels a preparation, whose end then never runs: Settings, Projects and a form's Cancel; a tab switch or close drops the read with the tab's other reads instead, and the tab reads quietly when shown again. A cancel once left the read noted, so Refresh pressed during Discard…'s review never ran once Settings opened and the tab was clicked back, or ran unasked at the end of a later preparation (`page_navigation::tests::a_refresh_a_cancelled_preparation_held_back_still_runs`, `a_tab_switch_or_close_drops_the_read_its_tab_asked_for`). A write in the shown repository reads for itself as it ends (`read_after_write`): Commit, Fetch and the other writes that change history refresh quietly, which also gives a selected working row back the preview Changes cleared as it opened, and an LFS download reloads only the preview it was asked from, if that view is still shown, so a view that has moved on keeps its preview and scroll. On the one serial executor each switch to Changes once queued a read behind a write in another tab; once the bounded queue was full the next read failed as busy and emptied that tab's rows, which the write's end, reading only its own tab, never restored (`page_navigation::tests::changes_opened_in_another_tab_during_a_write_reads_once_it_ends`, `changes_opened_while_a_review_is_prepared_reads_once_it_ends`, `a_commits_quiet_refresh_serves_changes_opened_while_it_ran`, `an_lfs_downloads_end_reads_only_what_its_view_asked_for`). Changes once refused while any write ran, from a toggle drawn and announced available. Projects still waits for the write (`show_projects`), since its every action, Back included, starts another operation or is refused while one runs; the header's Projects and History's Back to Projects are refused at once and say why in their tooltips once dimmed (`GitTurtle::refusing_with_reason`), a tooltip view read from the app each time it renders, so one already shown under a resting pointer gains and loses the reason with the look (`page_navigation::tests::a_pointer_resting_on_projects_reads_why_it_waits_while_a_write_runs`); the kit keeps a text tooltip as the pointer enters it. The review preparations `show_projects` cancels before that check are reads, which it ends rather than waits for. Opening Changes from History or Compare drops the plan a recovery, rebase or branch action is being prepared for there (`dismiss_recovery_read`, `dismiss_interactive_rebase_action`, `dismiss_branch_action`), so its form never opens over the working list as Amend last commit's once did; unlike a cancel, the preparation's read still ends as it would, keeping the busy state until then, and its end reads the working state Changes asked for, since the executor cannot stop the read and a read asked for at once would only queue behind it (`page_navigation::tests::changes_opened_while_history_prepares_a_plan_drops_the_plan`).

Capture the current focus handle when leaving Repository for Projects or Settings and restore it once after the retained content is visible. Preserve an editor or Find field's exact focus rather than substituting generic file-list focus. Keep file-history editors alive across these page transitions; opening another repository clears the old return focus. Back and the repository's own tab (`switch_repository_tab` on the open repository's tab: the tab strip, the tab menu, its shortcut or opening the project again) take up the page alike (`resume_repository_page`): File history's selected revision loads where its page landed while the repository was hidden, an editor whose preview landed then is built, focus returns, and held quiet reads start; Back then runs a working read still noted (`read_deferred_working`). Returning through the tab once only started the quiet reads, so File history opened just before Settings came back with its selected revision beside no preview of it. Theme changes update retained file-history and split-editor decorations in place. Retained inspection state must not retain live drag gestures.

Branch/worktree filtering and the branch Switch/Create target belong to the last successfully resolved canonical worktree. Clear both when a generation-accepted Open snapshot changes that worktree; preserve them on same-repository page visits, ordinary refresh, alias opens and failed opens. Commit drafts retain their independent per-worktree storage and restoration.

Quick Open's source inspector owns `file_focus` while the changed-file list is absent. Modal activation restores that visible destination after the dialog closes. A modal that records its opener in `modal_return_focus` as it opens, as the GitHub panel does, returns focus there as it closes (`GitTurtle::modal_return`), and the repair a frame later returns it to the same place; an opener no longer drawn, or the window's root, which shows no focus, gives way to the shown mode's own list. Native editor Escape bubbles to the app's Back handler when Find and editor popovers have not consumed it; closing Find alone keeps the source inspection open.

A right-click menu (`native_accessibility::PointerMenu`) keeps its open menu in its row's element state and records it, with the focus it returns to, in `OpenPointerMenus`. Its dismissal returns focus the menu still holds, or that a press outside gave an element holding the place it returns to (the window's root, `app_focus`), and then lets the menu go, with its write and resize observers, so a closed menu is neither built again by a write nor dismissed again by a resize. A row that stops being drawn while its menu is open drops that state, and the menu with it, without a dismissal, so the return also runs from the menu's release observer, which lives outside that state: focus on the released menu, or on nothing, goes back where it was, as `KeyboardMenu`'s blur returns it. The menu is drawn inside its row, so its overlay stops `RowActions` and `ManageNavigation` from reaching the list or tree, which would open a keyboard's menu beside it.

That element state is keyed by the row's element ID, which the menu takes as its own (its state lies at that ID and the row's, drawn inside it, at that ID twice), so a list whose rows can come and go keys each row by what it shows: Working Changes keys a file row by its group and every byte of its path, written as text one way only, so `sub` and `sub/`, which `Path` holds equal, are two rows (`workspace::working_row_id`), not by its status index, under which a menu passed to the next row when a refresh took an earlier file away. The IDs are made once per row of the status the rows show and cloned in each frame after (`workspace::WorkingRowIds`, `working_row_key`). A row builds its menu from what it shows (`PointerMenu::built_from`, the file's status entry alone): an open menu built from another entry, as after the file was added and edited outside the app, is built again in place from the row's current builder, which a write's rebuild then uses too, so no item acts on a stale entry. A write's start or end, and the reload or status read it asks for landing, build it again through `PointerMenu::follows_writes` alone, once each; keyed on the write's state as well, the menu was built twice for each. While the filter prepares the rows of a newer status or of its own query, the rows drawn are the previous ones, and the menu waits for the new ones (`PointerMenu::waits_while`): a write's reload landing or a changed entry builds it again only once the new rows are drawn, from them, while a write's start (`MenuInputs::starts_a_write`) or end builds it at once, refused, and a menu opened on the previous rows refuses its items until then, as a click on those rows refuses. Refused for the rows, each item states why apart from its command (`GitTurtle::working_rows_wait`, through `detailed_item`): the running write by its label once it looks busy (`operation_shown`), and before then and otherwise "Filtering…" for the query's rows or "Refreshing…" for a newer status's (`working_selection::Preparation`); every item once said "Refreshing…", for a filter's rows too and through a write, and later named a write as it started, inside the delay in which a write that lands sooner shows none of its busy look. No other menu names a write: what a write refuses in every other menu, and in a Working row's while its rows stand, is refused with no reason, `detailed_item` stating only the Working rows' wait and the conditions a row's own file sets ("Untracked files only", "After conflict resolution"). A menu built so is built again as that reason changes, which `PointerMenu::waits_while` reads through `working_rows_wait` and `KeyboardMenu::followed_by` follows too, as the write's busy look shows or a newer status that lands while the filter's rows are prepared has them prepared again as that status's (`Preparation::Status`, from `apply_worktree_state`): with no write starting or ending, either menu once kept saying "Filtering…" until those rows landed. Built again as a Stage's status read landed, before its rows, it offered Delete untracked file… for a file the read had found added; one that waited as a write started kept offering what the write refused until the rows landed. A menu opened before the rows began to be prepared keeps its items until a write starts or the rows land: each acts on its file by path, and Discard changes… and Delete untracked file… review it again before Git runs (`discard_plan` refuses an entry whose status changed). The pointer's place is kept from the row's origin, and the row writes where it lies as it is prepainted, before the menu, a deferred draw, reads it (`native_accessibility::RowPlace`), so the menu stays beside its row in the frame a refresh moves it. A keyboard's menu on a Working Changes row records the file its items were built from (`file_menu_row`) and is placed from a `ListRow`, read from the list's scroll as the menu is prepainted; the rows each refresh installs move it to its row's new place, build it again where the file's entry changed, or close it, returning focus to the list, where the row went (`follow_working_menu`). A write's start or end and an integration's pause or end run the same follow (`KeyboardMenu::followed_by`), so the menu is built again from the row's file as it then stands, never from the entry it opened with, which brought back Delete untracked file… for a file a refresh had found added; while new rows are being prepared it waits for them to land, but for a write that starts meanwhile, which builds it again at once, refused, again as the write looks busy, naming it, and once more as that write ends, stating what the rows are for (`WorkingMenu::waiting`, which the rows' landing builds it again from). A status read that selects the menu's own row again leaves focus in the menu; one that moves the selection off it (`select_working`), as a read that finds the file staged moves it to the Staged group, closes the menu and focuses the list. Either menu also closes, its dismissal returning focus, when its row is not drawn or moves where the menu, sized for the room where it opened, fits neither below nor wholly above it (`leaves_its_row`), where it would be pinned to the list's edge or clamped over its own row; the check is in the shared `RowMenu`, so it holds for every right-click menu (History, the navigator, changed files) as for Working rows, and a keyboard's menu opens with its row scrolled into view (`ListRow::reveal`). Neither menu's items hold a row's place: a Stage or Unstage finds the row by its path when it acts (`working_row_position`). The rows compare paths byte for byte wherever they find a file's row (`working_selection::same_path`). Status lists an untracked repository at `sub/` only once a tracked `sub` has left the index, so the two never share a group; the selection's `Key` and the confirmations' `Mark` still order and hash by `Path`.

Command-palette rows are bounded workflow descriptors; highlighting is inert, and activation rechecks live availability and captured repository identity. `shortcuts::SHORTCUTS` owns app bindings and their platform labels used by menus, tooltips and shortcut help; add actions there instead of maintaining parallel key tables. Help rows describe bindings without dispatching actions. Dialog rendering uses owned snapshots rather than borrowing its parent entity. Keep initial reads and focus restoration after the parent update/layout boundary, and suppress late read results when the dialog closes. Custom controls also need stable accessible IDs, roles, labels and selected/disabled states; visible text alone does not supply those nodes. See [command dispatch](../../../docs/command-palette.md) and [native semantics, display preferences and toolkit patches](../../../docs/native-accessibility.md) for their conditional contracts.

## Desktop observers

`desktop_text::start` installs safe defaults before its bounded initial wait. Linux portal setup, signal reads and `fc-match` fallback run in one app-owned background task; foreground application takes only the latest snapshot. Coalesce wakeups, cap work per signal batch and yield so a continuously ready source cannot starve cancellation. Focus regain requests one refresh and retries an unavailable portal, and so does a change to the user's fontconfig configuration: the same task watches `$XDG_CONFIG_HOME/fontconfig` (or `~/.config/fontconfig`), and that directory's parent while it does not exist, and requests a refresh once writes there settle for 250 ms, ignoring reads so `fc-match` cannot trigger itself (`desktop_text::user_fontconfig`). Do not introduce idle polling. Child queries have time and output limits, are read on the executor's timer rather than blocking a worker thread, and are killed and reaped when they fail, outlive their bound, are dropped or the app exits. A query ends once its child has exited and the pipe is drained, not when the pipe closes: a process another thread spawns while the child starts holds a copy of the pipe's write end until that process execs (`desktop_text::portal::tests::a_query_ends_with_its_child_while_another_process_holds_its_pipe`). The observer cancels and joins its worker during app shutdown. While Settings asks for the desktop's monospace font, the same task runs one bounded `fc-match monospace` per connection (at launch, on focus regain and when the setting turns on, never per portal signal), after that connection's first snapshot, so launch never waits on it. The task awaits each query, so at most one `fc-match` runs at a time and a focus regain during a lookup waits for it. Without a fontconfig cache that lookup scans every font directory first (about 0.8 s on the [cold-launch record](../../../docs/benchmarks/2026-09-29-code-font-cold-launch.md)'s host), so its bound is `portal::FAMILY_WAIT`, 4 s: Settings shows it pending until it answers, and unavailable only when that bound runs out. Turning the setting off, or off and on, stops a running lookup (`desktop_text::portal::tests`, `settings::picker_tests::the_code_font_row_stays_pending_through_a_slow_lookup`). It accepts the first listed family that the toolkit's `all_font_names` includes and that draws basic Latin at one advance, and never looks up an unlisted name, because the toolkit caches a failed lookup for the process. Each reply carries the generation of the setting it answers, and `apply_code_font` drops one for a setting since turned off or off and on (`desktop_text::tests::the_code_font_follows_the_setting_and_survives_theme_changes`).

`appearance::omarchy` owns the desktop's Omarchy theme on Linux in one app-level global that the picker card, the Follow system switch and `apply_appearance` read. It reads `~/.local/state/omarchy/current/` on the background executor at launch (launch waits up to 200 ms for that read only when the Omarchy theme is selected), on focus regain, when a watch starts and when the card is chosen. A choice reads first and applies only what that read finds; if the read has not landed within 100 ms (`settings::OMARCHY_CHOICE_WAIT`, a GPUI timer), the cached palette applies, then the read's own result when it differs. It watches that directory without recursion while the Omarchy theme is selected, and while Settings is open: Settings starts the watch while it offers the card and keeps a running watch when a read withdraws the card (`theme/` gone for longer than the quiet period mid-switch, or a state migration), so the theme coming back offers the card again without a focus return. Closing Settings drops the watch unless the theme is selected. While the card is not selected, a watched reread updates its caption and miniature and applies nothing. Rereads run one at a time: a watched write that can change the theme (`theme/` or `theme.name`, never `background` or `next-theme`) waits for a 250 ms quiet period on the GPUI timer that each further write restarts, capped at 2 s. A focus return during that period joins it rather than reading a half-done switch, and every request queued meanwhile joins the one reread. An event on `current/` itself marks the watch failed, and the next focus regain watches the directory again. Each reread carries a generation and `finish` drops a result older than the latest one started; a result that changes nothing leaves the global untouched, so no observer runs and nothing is applied (`appearance::omarchy::tests`). Nothing is written under that directory.

Desktop rendering preferences and text factors are app-global inputs, while `GitTurtle` windows apply changed geometry to their own active and retained content. Wayland applies the desktop text factor; X11 already obtains window scaling through the toolkit. Do not persist desktop changes as user-selected app sizes or apply the factor twice. The [Linux platform limits](../../../docs/linux.md#platform-limits) own source precedence and unsupported rendering modes. Portal/process regressions live under `desktop_text`, and `repository_tabs` exercises multi-window/retained geometry; native platform evidence remains separate.

## Ordinary history paging

`history_paging` keeps up to 5,000 rows and 64 MiB of commit/graph metadata in the visible window, plus at most one selected commit outside it. Older requests continue the same immutable traversal in 500-row pages; they never reread all previously loaded metadata. On reaching the window bound, Older advances to the next window while retaining the selected inspector/Compare identity. Previous navigates the captured ordering; returning to an earlier window rebuilds one pinned stream and discards bounded pages until its offset. Latest and Show latest explicitly capture current local tips and return to row zero without selecting a different commit. This backward restore is linear in depth; there is no permanent 10,000-row ceiling and no full-history metadata cache.

The worker owns one `HistoryTraversal` and `GraphCursor`. Incremental graph preparation preserves frontier lanes/colors across page and window boundaries, commits cursor state only after cancellation checks, and latches an honest node-only fallback if its lane/edge allowance is exceeded. The graph column has a bounded automatic viewport (25% of the history width, between 112 and 280 points, while honoring larger saved widths); shared horizontal lane navigation preserves actual spacing without allowing offscreen ancestry to push commit messages away.

Search retains/restores ordinary paging state. `history_updates` keeps a bounded, per-worktree observation separately from the paging cursor and selected inspector. Quiet refresh follows row zero only in ordinary History at the top; Compare, Working Changes, older rows, deep windows and search retain their exact history, selection and content. History's scope toolbar cues a pending update the list does not show, without a row of its own (`GitTurtle::history_update_cue`): its words beside the count where they fit, a polite status, and an accent dot on Latest, whose name and tooltip lead with the cue and which reads current local tips and ends it. A quiet read that History follows installs the rows at the top and ends the cue (`history_updates::State::observe`), so the reads after a Pull or Push from History's top end it; one read elsewhere adds to it. The shared update row it replaced, above every mode, offered Show latest and Dismiss and pushed the page down 35 px; Compare and Working Changes now show the cue when Back or History returns to the list. The Latest control always reads current local tips, including when the visible window starts at zero. Explicit actions leave a captured search; passive reads preserve both its results and its normal-history return context.

New counts are exact only for complete histories within one 500-row page, or a bounded single-parent chain that proves extension of one previous tip. Merges outside complete coverage, removed refs, rewrites and page-limit uncertainty say History updated. Repeated changes coalesce; unchanged observations do not repeat a notice. Repository tabs retain their own observations and commit receipts; opening a scope resets its observation. Successful commits retain an explicit View commit receipt, resolved from the returned OID through a bounded worker read. That action selects the actual commit while leaving a subsequent composer draft saved. Passive updates never select a different commit or enter Compare. `history_page_frame_ms` measures the page handler through its next frame callback, excluding pre-handler input dispatch, OS presentation and completed GPU work. Worker elapsed time remains a separate metric.

## Search and retained inspections

Repository-wide search pins scope tips across pages, shares the replaceable read worker, and propagates cancellation to the core history process. Retain the ordinary history separately and restore it on clearing search. Foreground commit/file activation pauses search without discarding its results or cursor. Keep Restart explicit so users can search new commits/current tips after a write while quiet refresh preserves the captured search. An explicit History Refresh also restarts scope. Distinguish exhaustion from page, scan, time, byte, and UI-retention bounds; never present a bounded partial scan as an exhaustive no-match result.

File history uses an explicit path and immutable anchor, preserves rename paths/absent sides, and restores the preceding repository context on Back. Its first-parent lineage and pagination limits stay visible. Attribution and line history also use bounded worker reads and check repository, target and selection generations. Attribution owns a separate accessibility focus handle. Nested inspections restore the preceding comparison and line selection; explicit repository/scope/write transitions unwind them.

Return contexts retain conflict views and subscriptions alongside text editors, including draft cursor state. Returning to an interrupted Quick source load reissues `TrackedPreview` with its captured scope and byte-safe path. Absent comparison sides and unavailable working-file history anchors never fall back to the normal history selection. Closing the last retained inspection resumes queued passive refresh after the current handler finishes.

Changed-file path filtering shares cached row identities with renderers. `path_filter` normalizes old/new paths and matches queries on a lazy serial background lane, with cancellation checkpoints and explicit 100,000-path, 16 MiB index, 64 KiB single-path and 4,096-byte query limits. Replacements call `refresh_file_filter`; clears reset its state. Generation and file-snapshot identity checks reject stale replies, and a matching reply clears a selected preview only if that file is hidden. While a History query is pending the list keeps the rows the last reply left, files of the same snapshot that stay actionable, so typing never draws an empty list or a false "No matches"; "Filtering changed paths…" shows only for a snapshot with no rows yet (`path_filter::tests::typing_a_filter_keeps_its_rows_until_the_answer_lands`). History's queries coalesce: one job runs in the lane, and the newest query typed meanwhile waits for its answer, replacing any that waited before it, so typing faster than the worker answers never fills the lane's queue and is never refused as busy (`twenty_keys_typed_while_the_worker_runs_coalesce_to_the_last_query`). Rendering does not scan or lowercase paths. New revision inspections start with an empty path query; Back restores the preceding query, text review options and editor entities. Working Changes shares this executor and normalization code: status snapshots are shared through `Arc`, directory grouping and matching run off the UI thread, and refreshed entries cancel the previous index. While a result is pending the list keeps drawing the previous result's rows and counts, so it neither empties nor moves: they are drawn only, and selection, keys, copying, menus and row departures see no rows until the new ones land (`actionable_working_rows`), with selection actions disabled. Rows kept across a status with other entries index the earlier status, which `FilterState::supersede` keeps with the cursor among them until the new rows land; a retained tab keeps rows only with their own status and counts. "Filtering working paths…" shows only before a list's first rows. A query that matches nothing leaves the list only its two empty headings; the list draws `working-no-match` in their place, an `EmptyState` with Clear filter (`clear_working_filter`), decided from the shown rows (`working_no_match`) so it stays while a newer query's rows are prepared, with a floor that keeps it whole (`working_no_match_floor`) and none of the selection controls above the list changing height. Accepted results reconcile literal path/area identities and quiet-refresh scroll anchors. Counts and conflict summaries are prepared with the rows. Filtering never narrows the meaning of Stage all or Unstage all: those actions are disabled while a query is present.

Working Changes previews use their own status-path filter. The retained History
path query never filters a working preview, including quiet refresh results;
returning to History reapplies that query to the retained changed-file list.
Superseded History filter replies cannot clear a Working Changes selection.

## Local refresh

Filesystem callbacks only enqueue bounded local events. Resolve actual private/common Git directories and register watchers outside the UI thread; do not poll repository trees or invoke Git in the callback. Coalesce bursts, ignore passive access/lock noise, and defer quiet reads behind active previews, search, file-history inspections, status work or writes. Preserve refresh epochs and selection/status generations so superseded results cannot apply.

Quiet snapshots update local metadata without navigating away, clearing search, or replacing an unchanged immutable preview. The quiet read a write asks for as it ends (`refresh_after_write`) carries `LocalChange::after_write`, which the watcher never sets: until the read that carries it lands, menus refuse writes as while the write ran (`GitTurtle::write_unsettled`, folded into `native_accessibility::MenuInputs`), so none is built for the state the write left behind, and a file saved outside the app dims nothing. A write that changes only the working state (Stage, Unstage, Discard, Ignore, Delete untracked file…, Resolve, a stash's recovery) reads the status again as it ends rather than asking for a quiet reload, and menus wait for that read to land as well (`GitTurtle::status_after_write`, the `work_generation` it was asked at). A read that replaces it (`refresh_worktree`), as Refresh or showing Working Changes starts one, takes that mark with it, so menus wait for the new read instead; replaced unmarked, the write's read was no longer counted, and a Working row's open menu was built again from the status the write had just changed before either read landed. A reload that another page or an open inspection holds off (`GitTurtle::quiet_reads_held`: Settings or the hub, File history, a revision inspection or Blame) refuses nothing until it can run, as the window returns to the repository or the inspection closes and starts it; returning through the repository's own tab (`switch_repository_tab`, from the tab strip, the tab menu, its shortcut or opening the project again) starts it as Back does, where it once waited for the next local change with every menu refused, and closing Blame starts it on the next frame, as closing File history does. A history load or search, such as the read selecting a commit or a working row starts, puts a running reload back to wait (`cancel_automatic_read`) and starts it again as it ends, or the read that replaces it does, ending as well where the worker drops it unanswered with no newer read in its place (`request`, which once left the window loading and the reload waiting with every menu refused; an Open so dropped fails as an interrupted read, the hub no longer busy and saying why, where it once stayed busy with no error), and a read stopped with nothing of its own to start (`invalidate_read` as History's file filter hides the selected file, as Working rows land without the selected row, or as a working row's side has nothing to show) starts it at once, so menus stay refused through it and no longer than it: counted as held, a reload waiting for a selection's read refused nothing, so a commit's menu opened with Down, Up and Shift-F10 as an Undo's reload ran offered Revert and Undo of the commit the Undo had taken away, and an open menu went available, refused and available again. A project row's Open project reads `operation_busy` alone, since opening another project reads nothing the reload brings, so `MenuInputs` follows a write's end as well as its reload; the row's actions button (`project-row-menu`) follows writes as its right-click and keyboard menus do, where it once read the write only as it opened. HEAD counts among `MenuInputs` only for a commit's menu, given its commit (`follows_head_of`, `KeyboardMenu::following`'s `commit`), as whether that commit is HEAD, which adds Amend and Undo; counted for every menu, a branch's, a worktree's, a project's or a working row's open menu was built again whenever HEAD moved, its keyboard's cursor back on its first item. Refresh changed mutable editors in place and retain manual conflict drafts by conflict identity. A vanished scope keeps the displayed history with an explanation, reported once: after it is dismissed, later quiet refreshes and accepted writes do not raise the same vanished scope again until a snapshot resolves a scope. An explicit Refresh (or Show latest, or a restored tab) resolves the branch or worktree scope again; when it is gone the worker reads All history instead, and the page lists the repository's commits with one polite status naming the vanished scope, never "Could not open repository" or an unavailable tab. That status wraps to as many lines as its text needs beside its Dismiss action, so a long branch name or worktree path is read whole at every interface text size. An unpinned History search that finds its scope gone reports the scope change rather than a failed read. Partial coverage remains visible through a quiet footer status with Refresh and copyable Details; it is separate from Git operation failures and clears when coverage recovers. Neither a filesystem event nor focus regain may trigger a write or network action.

Linux registers essential private/common Git roots and refs before bounded working-tree coverage. Core prepares byte-safe tracked-path ancestors and Git ignore matchers (nested `.gitignore`, common `info/exclude`, and effective global excludes); ignored trees are pruned, while tracked paths inside ignored directories remain covered. Directory symlinks are not traversed. Missing/replaced directories during enumeration are ordinary races, not watcher failures. Existing metadata watches survive permission, OS-watch, directory-count, or scan-budget constraints. Native recursive subscriptions remain in use on other platforms.

Directory creation and renames add only the affected subtree. Coalesced index events update tracked ancestors; ignore edits reconsider the affected subtree, and external excludes/config changes reconsider coverage. Lost events allow one bounded reconciliation per continuous burst. Scans stop at 16,384 registrations, 200,000 entries, or two seconds; at most 256 omitted roots are retained. Freed registrations retry omitted roots once, while explicit Refresh or focus regain can reconnect degraded coverage. Ordinary quiet reads do not repeatedly rebuild an unchanged degraded watcher. No timer polls the tree. Core watch policy bounds tracked paths to 100,000 and source path/rule bytes to 16 MiB, with a 1 MiB individual ignore-file bound; Git subprocesses retain their existing passive deadlines and output limits.

## Retained commit messages

The inspection's `inspector_message` belongs with the existing
`file_history::ReturnContext`, including nested File History and warm tabs. File
activation and Compare/Back keep its OID and viewport. Selecting a different OID
invalidates its display pieces and starts at the beginning; replacing a
repository or closing its tab releases them. Projects/Settings remove the view
without discarding its state. Cold restoration deliberately starts the message
at the top, rather than persisting a second copy of commit text. Copy callbacks
revalidate the displayed OID against the current loaded selection.

## Repository tabs

`repository_tabs.rs` owns canonical worktree tab identity, saved bookmarks, and retained `ReturnContext` chains. Each window has one active repository reader/watcher; switching invalidates pending reads, drops the branch comparison Merge… or Rebase… asked for and ends its busy state with it (`cancel_integration_comparison`; dropped alone, "Comparing branch tips…" once stayed for good and held every later write and working read, `page_navigation::tests::a_tab_switch_ends_the_branch_comparison_it_drops`), releases its history stream off the UI thread, pauses PDF/model/Markdown work throughout retained contexts, freezes GIF playback, and restores the new tab before a passive rescan. A selected immutable commit can remain outside the visible history window. Opening aliases deduplicates after core discovery; linked worktrees retain separate tabs and drafts.

Warm restoration keeps the root focus attached while the destination tree changes. After layout, restore the exact retained control only if it still belongs to that tree; a removed tab/control falls back to the visible history or file pane. A newer focus change, repository switch, or modal supersedes that one-time restoration.

Up to eight tabs in a window share a conservative 512 MiB retained-state admission allowance, including nested inspection/source/editor content reservations, patch presentations and the decorations Compare's unified patch keeps with its editor. Exceeding it refuses switching until a tab is explicitly closed. The 16 MiB application-data session restores cold identities and an addressable top comparison, not decoded content or every nested inspection. Accepted operations stay in that window's serialized executor with their captured repository; late result and draft updates route by that path. See [the tab workflow and exact restart bounds](../../../docs/repository-tabs.md).
