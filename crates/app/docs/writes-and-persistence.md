# Writes and persistence contracts

Read this when changing or reviewing working status, write forms, operation outcomes, projects, settings or draft storage. These contracts describe user interactions in GitTurtle. Engineering authorization follows the [root agreements](../../../AGENTS.md). Git command behavior belongs in [core write guidance](../../git-core/AGENTS.md).

## Captured actions and outcomes

Hub events carry Open/Clone/Create/Back intent; clone/init and destination checks run off the UI thread. Preserve native-picker path bytes, user-edited form values, cancellation and nearby errors. A submitted write keeps its captured repository/target and cannot be replaced or retried by later navigation. Show busy state and refresh relevant status/history after success or failure. The busy look (the header's progress label and Cancel, the tab's "· working", "Refreshing…" and the disabled look of the controls a write and the reads after it make unavailable) waits `workspace::BUSY_LOOK_DELAY`, 200 ms of a busy spell that runs from the write through its status read to its rows (`GitTurtle::track_busy_look`), so a quick write never flashes it; those controls refuse at once whatever they look like (`write_from`, `depart_working_row` and their own handlers), and `workspace::refusing` announces them unavailable to assistive technology at once while their disabled look waits; a dialog decides both through `workspace::dialog_refusal`, through `workspace::dialog_refusing` where the window builds the dialog in its own render, and its handlers refuse through `GitTurtle::dialog_refusal` before they change anything, off the Repository page as during a write, so a control announced unavailable never acts (Tags' rows, Create tag…, Delete local tag… and Push to… once checked only the repository and the write); Create tag draws its own footer so that Review tag follows the write (`tags::ReviewTag`), where the kit's footer draws its OK available through any write and a press set the form's error; that is the direction for the dialogs whose confirming action is still the kit's OK, which look available through a write and answer a press with their form's error (the branch forms' Review action and Review settings, Review download, Review amend, Review stash, Save profile, Preview rule and `confirm_git_write`'s confirmation); a menu built during the delay disables what the write refuses. `SerialExecutor::submit` and `submit_controlled` preserve accepted writes after a dropped reply; `submit_read` may skip superseded queued status reads. Preference persistence uses a separate executor instance.

`RepositoryOutcomes` scopes operation errors/notices to the last successfully resolved canonical worktree. Only a successful, generation-accepted Open snapshot can clear the previous worktree's captured outcome. Failed opens and aliases of the same worktree preserve it; an outcome published after Open was dispatched also survives its reply, including Clone/Create completion notices.

A write a control asks for confirms on that control (`GitTurtle::write_from` with a `confirmations::Origin` holding the control's `copy_feedback::Mark`; the actions, marks and origins are `workspace::confirmations`). Only Git's reported success confirms, and only while the write's repository is still the one shown on the Repository page: the control reads its past tense for 1.5 s through `copy_feedback::confirm`, which also announces the outcome once, the status line records it, and `operation_notice` stays down so the outcome is announced once rather than also by the window-wide notice. A heading action the write leaves unavailable, Stage all on the group it emptied or either one while the reads after it are pending, stays disabled and inert but draws its confirmation in its resting label colour (`Palette::control_label`, set on the Button, which the kit replays over its disabled colours) and takes the disabled colour when the confirmation ends. The status line keeps every write outcome it records, one a control confirms or not, for `copy_feedback::RESTORE_AFTER` over the status the reads after the write set (`GitTurtle::record_outcome`, drawn by `status_line`), so the refresh after the write cannot replace it while its control still reads its confirmation; a newer outcome replaces it, a submitted write ends it, and it is drawn only while its repository is shown. Once the rows a Stage all or Unstage all produced arrive, `GitTurtle::reveal_confirming_heading` brings the heading whose control confirms into the Working list's view, the least move that keeps the selected file's row in view too, and nothing where both cannot be seen (`heading_reveal`): it decides from the list's last layout and places the heading through the list's own deferred scroll, and again when the list's measured height settles a frame later (the composer is measured again) or its row count changes, so the heading lands whole in the viewport it is drawn in. A Fetch or Pull whose `WriteOutcome::up_to_date` is set still confirms with its own word, while its announcement and status line say "Up to date with ‹remote› · nothing new", or for a Pull "Up to date with ‹remote›/‹branch› · nothing new". A review dialog's confirm (`confirm_git_write`) takes its origin from `confirmations::reviewed`: a tracking branch created with its switch marks the picker for the new branch (`confirmations::picker_created`, whose tooltip says Created), and one created without it confirms with `Origin::StatusLine`, which marks no control but still announces once and records the outcome. A failure or an uncertain result keeps `operation_error`, a write submitted with plain `write` (the command palette, multiselection), any other review dialog's confirm, or a write completing for another tab keeps the window-wide notice, and nothing is retried. A mark names the control and what it acted on, so a quiet refresh, another target or another repository never shows it: a working file's Stage marks that file's row in Staged, where the file arrives (`Mark::per_subject`), and Unstage its row in Unstaged; Stage all and Unstage all, Create and Switch mark themselves for the repository; Fetch, Pull and Push mark the remote and branches they used, so editing Targets leaves the next target at rest; a switch from the branch picker's menu marks the picker for the branch it names.

The repository action bar stays visible in History, Compare and Working Changes. `git_actions_open` controls only the Targets fields, which start collapsed so ordinary history and comparison retain their content height; preserve the choice across Projects/Settings visits. Navigator branches filter history; the current-branch menu explicitly checks out a local branch. Build its bounded choices only when opened, keep find/create available, and reject callbacks if the repository changed since opening. Derive remote defaults again when branch/upstream changes without overwriting edited targets on ordinary refresh. Tooltips identify the target and Pull's fast-forward-only behavior. Display remote URLs through `display_remote_url` to omit embedded credentials.

Branch management belongs in the compact picker and navigator context menus; ordinary navigator clicks remain browse-only. Branch, remote, integration and recovery forms prepare consequences off the UI thread, retain input on failure, and confirm the captured repository and target through `open_alert_dialog`/`confirm_git_write`. The dialog exposes its actual Review/Confirm and Cancel buttons. Keep selected-commit actions in its context menu or inspector and working recovery actions in the Changes inspector. Respect branches occupied by other worktrees and show destination/upstream changes before submitting them.

Tag and ignore actions also prepare exact captured reviews before entering the existing operation executor. Authentication prompts and cancellation are transient and operation-scoped; credentials never enter preferences. Preserve configured authentication mechanisms and explicit process cancellation described in [authentication](../../../docs/authentication.md). Native menu and editor/Finder handoff actions remain explicit local interactions.

## GitHub collaboration

`github` owns the provider client, transport and stores; `github_view` owns native PR inspection and review forms. Its [collaboration contract](../../../docs/github-collaboration.md) is the authority for account connection, explicit network actions, pagination, inline positions, durable attempts and recovery. Opening or warm-restoring the panel uses local state only. Accepted outbound work uses the existing operation executor with captured account/repository/head/base identities; a pending attempt must be stored before sending. Lost replies and uncertain outcomes preserve drafts and require explicit verification, never automatic replay or remapping to a newer head.

Review conversations use authoritative GraphQL thread state and viewer permissions. Reply/resolve/reopen confirmations capture stable account, repository, PR, thread and opening-comment identities plus the reviewed head/base; preflight revalidates them before one mutation. Independent reply drafts share the serialized preference saver, flush at navigation/close/shutdown boundaries, and restore only into the same usable context. Stale or unavailable targets retain copy recovery. Confirmed reply receipts live with durable attempts, so failed preference cleanup cannot revive exact completed text; later replies and pending/error/resolution outcomes preserve earlier proofs. Receipt-bearing attempts are protected from eviction, and proof/entry/byte limits refuse growth without discarding recovery evidence. Empty completed-reply snapshots remove only their captured store entry through the same coalesced saver, preserving newer edits and freeing bounded draft capacity.

Credentials stay in the platform credential store and transient transport state, separately from coalesced text drafts and attempt records. Draft persistence uses the preference executor and shared bounded store reader; invalid stores remain recoverable. PR creation does not implicitly push, and captured local comparisons do not implicitly fetch. Native offline fixtures establish UI/model behavior only; actual hosted account and write evidence remains separate.

## Working changes and recovery

Distinguish HEAD-to-index from index-to-worktree previews, including files present in both lists. Pass both paths when staging a rename. Passive status/preview reads stay read-only. Real operations use core's stale-checked plans and commands; mutation checks use disposable fixtures. **Discard changes…** and **Delete untracked file…** in a working row's context menu prepare a `DiscardPlan` on the operation reader for that exact row, then confirm the captured repository and command through the discard review dialog. Keep the loss warning and destructive action distinct, make long paths inspectable, and bound the scrolling content at enlarged text sizes. Navigation cancels pending preparation; confirmation rechecks the captured repository and generation and submits at most once. Both the staged and unstaged rows of one file offer the same whole-file revert to HEAD; a conflicted row keeps a disabled item.

Conflict and rebase-message drafts use `recovery_drafts.rs` and the existing `commit_drafts::CoalescingSaver` on the preference executor. The independent atomic store preserves exact UTF-8 text and byte-safe canonical worktree/file identities. Conflict identities include operation, HEAD, stage OIDs/modes and raw working bytes; message identities include the complete index and Git message/checkpoint. Compute source hashes on the worker. Valid recovery is explicit; stale drafts are copy-only and remain recoverable. Saving/Saved/error status is visible. Retain at most 256 entries and 64 MiB of text, refusing overflow without eviction; completion, abort, removal and movement retain text until explicit discard. Stage external edits or save-and-stage manual results only through the explicit resolution command. Recovery uses detected Git state; stash-apply conflicts have unresolved files without a sequencer Continue/Abort operation.

Block parsing and navigation follow [conflict-block review](../../../docs/conflict-blocks.md). Block choices modify the result draft; Save draft writes without staging, and Save and stage refuses remaining markers. Preserve the parsed generation when applying a block choice and keep source panels and result labels explicit. [Interactive rebase](../../../docs/interactive-rebase.md) uses the same conflict path and operation bar with native pending-message review.

Stash inspection owns separate bounded metadata/preview readers and never replaces the workspace comparison. Show staged, unstaged and untracked snapshots separately and load only a selected file. Restore-index and include-untracked are explicit choices; restoration never removes a stash, and Drop requires a separate captured-entry confirmation. Preserve core's contextual failed-restoration summary: verified conflict/retention state belongs in the compact error, both Git streams and exit status in Details. Do not classify uncertain process outcomes as confirmed conflicts or claim retention when its recheck failed.

Amend retains edited fields on failure and the exact original message when unchanged; edited messages use the ordinary composer format. Undo-local, revert and cherry-pick use prepared core plans rather than inferred UI safety. Merge replay/revert requires an explicit mainline parent. While a merge, rebase, cherry-pick or revert is paused, every recovery plan refuses in core, so the app refuses first: the menus that offer Revert, Cherry-pick, Amend, Undo and Save changes to stash…, a button's, a right-click's or the keyboard's (`KeyboardMenu`), disable them and are built again in place when an integration pauses or ends, as when a write starts or ends; a commit menu's handler refuses before asking for a mainline and `read_recovery` refuses without reading a plan, each reporting the core's refusal (`GitTurtle::refuse_while_paused`), so Enter in a keyboard's commit menu while paused, whose items take no Enter, says why, leaving the menu open (`KeyboardMenu::refuses_while_paused`). Stashes' Review restore… is the exception: it never refuses from the pause the window read last but has the core prepare the restoration (`GitTurtle::prepare_recovery`), whose plan reads the pause itself, and Stashes stays open with its stash selected until that answers: a plan closes Stashes as its review opens, and a refusal replaces the footer note beside Review restore… with its reason, a fresh line announced at once on each refusal and shown nowhere else, static text whose node reports the part of it the stacked detail draws (`native_accessibility::static_text`), as the note that its pause has ended does. Stashes records what it asked (the stash's object, Restore staged state and its own selection generation) with the window's recovery read: choosing another stash or page, the other Restore staged state, or closing Stashes (the browser's release, however its dialog closes) cancels that read (`GitTurtle::cancel_recovery_preparation`), while the stash shown chosen again, by its row, Up on the first row or Home, is neither read again nor cancels (`StashBrowser::select_stash`). Reading it again would check nothing that acting on it does not: what it holds was read by its objects, which never change, and whether it is still saved where the list put it is checked again in core by what acts on it, Review restore…'s plan (`stash_apply_plan`) and Drop…'s write, each refusing in its own place, the note or the window's error, once a terminal has changed the list. A plan or refusal that no longer answers what Stashes shows is dropped (`StashBrowser::answered`), never shown under another stash or after Stashes has closed. While that read still runs (`StashBrowser::preparing`, read from the window's recovery generation and task rather than a flag only the answer clears), Review restore… names itself preparing at once and reads "Preparing…" once the busy look shows, both labels laid in one cell so its width, and the footer beside it, hold (`StashBrowser::review_restore`). Stacked beneath the list, the refusal, or the note that its pause has ended, keeps the lines the detail holds beneath Review restore… whole with its ring, two or one, chosen from the detail as each frame lays it out, and its reveal never scrolls the Review restore… just pressed out of view (`reveal_note`); beside the list it keeps two. The reveal carries its cause (`NoteReveal`). A press's answer, a refusal or failure (`StashBrowser::refuse`), carries the focus the press found (`window.focused`, held weakly) and is revealed while focus stays there, as well as while Review restore… or nothing in the detail holds it: a pointer's press focuses no kit Button, so a click on Review restore… leaves focus where it was, on the saved files or a document's open control, and its answer lay below the fold unseen. Once the keyboard has moved focus onto another of the detail's controls while Git prepared, as on a large stash, the answer is announced but not scrolled to, as the end of a pause is: revealed wherever focus lay, a late answer scrolled the saved files Tab had just revealed out of view. The end of its pause, which any status read finding it ended brings (`GitTurtle::integration_ended`), is revealed only while Review restore… or nothing in the detail holds focus (`FocusReveal::holds_focus`, the controls the detail last drew, a document's open controls among them through Stashes' opener, `system_preview::Opener::revealed_by`): with focus on another of the detail's controls, such as the saved files, a file's text or a document's open control, it leaves the detail where it is, announced but not scrolled to. Any answer but the paused refusal, such as a Git call's stderr of one line or many, shows only its first line that says anything there, and Details… beside it opens the whole report with Copy details above Stashes (`integration::show_error_details`, as the window's error's Details… does); a report with no such line says "Git could not prepare this restoration." with no Details… to open it, so nothing raw or unbounded reaches the footer in either layout and nothing the note clamps is left to a tooltip the keyboard cannot open; the paused refusal, in the core's words and replaced once its pause ends, keeps its whole text in its tooltip and name, with no Details… to vanish from under the keyboard. Where the core's answer and the window's pause disagree, a refusal for a pause the window has not read or a plan where it reads one, the window reads its working state again, quietly. Those refusals read the pause the window read last, which a merge finished in a terminal can end before the local watcher's read lands, or a retained tab can restore, so each also asks for a quiet read of the working state through the local-refresh path, never trying the action again; the next try reads that pause, and a form's refusal is an assertive alert, announced again each time the form opens with it (`native_accessibility::refusal_line`), and a status read that finds it ended (`GitTurtle::integration_ended`) replaces an open Amend or Save changes to stash… form's refusal, or the open Stashes' note, with "The paused operation has ended. Review again to continue.", a polite status, and ends the window's error that refused so. Never silently retry an accepted write.

## Preferences and commit drafts

Scope drafts to the resolved canonical worktree after discovery. Persist Title and Description independently from settings/recents through the serialized, coalescing draft saver. Build the message as title, blank line, description without trimming user formatting. Retain text on failure; clear it only when a successful commit matches the submitted text. A failed draft save must retain pending data without overwriting a newer edit with the older failed snapshot.

Commit and recovery draft savers keep their actual accepted completion at app lifetime. Normal application shutdown awaits that completion even after the final window disappears, including a coalesced final edit when the preference queue is full. An earlier repository-session save or an extra queue barrier is not a substitute for the draft save. GPUI allows a 200 ms shutdown grace; a confirmed Saved result remains the durable boundary for slow or failed I/O and forced termination.

Project display names are app data keyed by the canonical worktree root. A name replaces the folder name wherever the client lists that project and never touches the folder, the repository, or Git configuration; clearing it restores the folder name. Validate presentation only (one line, 1-128 bytes) and bound the stored count, refusing a new name at the limit rather than evicting one. Opening Rename focuses and selects the saved name; Cancel discards unsaved edits. The current-project action waits for canonical repository discovery and revalidates its captured target. Saving disables input and duplicate submission, keeps the dialog open, and shows validation or persistence errors beside the retained text. Only a successful reply for that dialog closes it. The save merges into the latest stored preferences through the serialized preference executor, so it cannot drop settings, recents or drafts; malformed, duplicate or excessive stored names refuse subsequent writes instead of silently losing labels. Visible names, accessibility labels and tooltips retain the physical path where needed to distinguish projects.

The project list is app data: known project paths, user-named groups, their nesting and each group's collapsed state. Opening a project adds it at the top level of that list, so the list keeps projects that the ten recent entries no longer hold. A store written before the list starts from the recents once; an emptied list stays empty. Bound the list at 64 groups, 256 projects and 5 nesting levels, and refuse a new group or project at a limit. A full list drops its oldest ungrouped project and keeps grouped ones, because the user placed those. Removing a group keeps its projects and subgroups at the group's position. A group can never move inside itself or one of its own groups. Validate group names as project names are validated. The save merges into the latest stored preferences through the serialized preference executor; a malformed, duplicate or excessive stored list refuses subsequent writes instead of silently losing groups. The list never moves, creates or deletes a folder on disk.

The pane presents the saved tree sorted by display name within each level, groups first, and rebuilds its rows only when the library or a project name changes; the saved order is untouched and still decides which ungrouped project a full list drops. Edits show at once and are written through the preference executor as numbered saves, in one sequence with the recent-project saves that also return the list: only the newest save's successful reply may replace the presented list, and only the newest pane save's reply sets or clears the pane's error, even when an older reply is handled after it, so an older reply cannot undo a newer edit. A recent-project reply never replaces the list or touches the error. It adds the opened project to the pane's current list unless the pane already listed it when the save was submitted, so a removal made since stands, or the store refused it; when a pane save numbered after it wrote the whole list without the project, or a full list dropped an ungrouped project to fit it, which out-of-order replies can make differ from the store's choice, the merged list is saved again, unless the newest pane save failed: then nothing is written until the user's Retry saves the edit and the project together. A refused edit or failed save stays visible inside the pane with Retry, keeping the edit on screen rather than reverting it silently.

A missing store is a first launch. `Preferences::load_at_launch`, called only by `main`, reads the store before the application starts and never writes it; when the file does not exist it fixes, once per process, the settings that store stands for (`AppSettings::for_first_launch`): on a Linux desktop running Omarchy (its current theme's `colors.toml` is a regular file, the rule that offers the Omarchy card) the Omarchy theme with **Use the desktop's monospace font** on, and the defaults elsewhere. Every writer's `load_for_write` that still finds no store starts from those settings rather than `AppSettings::default()`, so the first save of anything (opening the first repository, a draft, a project name) records the desktop's defaults and the next launch keeps them. Only a missing file counts: an existing store keeps its stored theme whatever the desktop runs, including one on the default theme, and a store that cannot be read or parsed starts with the defaults without fixing any.

Custom themes are app data in the preference store's `custom_themes` section, beside the project list: each entry has a unique `u32` id, a name, a built-in base and all 21 semantic tokens as lowercase `#rrggbb`, keyed like the theme export document. Bound the section at 32 themes (`MAX_CUSTOM_THEMES`) and refuse a new one at the limit rather than evicting one; a new id is the largest existing id plus one. Names follow the project-name rules (one line, 1-128 bytes), never equal a built-in label and are unique ignoring case; they are stored trimmed. `settings.theme` is a `ThemeSelection`: a built-in keeps the bare string (`"nord"`) so the `settings` object stays byte-compatible with version 5, and a custom theme is `{"custom": id}`. `AppSettings::effective_theme(cx, custom_themes)` returns the applied `ResolvedTheme` for the selection the desktop honours (a Linux Omarchy selection without its reader is the default theme), through the rule in `resolve_selection` that tests reach as `resolved_theme`. Not following the system, that is the selection's palette; a selection naming a missing id resolves to the default theme without rewriting the file, and the picker shows that default as selected until the user chooses a theme. Following the system, a light appearance selects Braden and a dark one keeps a dark selection (built-in or custom, judged by `Palette::is_light`) and otherwise Midnight. `Preferences::save_custom_themes` runs on the preference executor, rereads the disk store and replaces only this section, so settings, recents, drafts, names and the project list saved since the caller loaded its copy survive; every other writer carries the disk's section through unchanged. The theme editor is its only caller: it submits the edited list, counts its pending saves, and replaces the window's `custom_themes` only from its own replies, so a preference save from elsewhere never disturbs an open draft. A failed save leaves the editor open with the error beside Save; a successful one selects the saved theme through the ordinary settings save, and deleting the active theme selects its base the same way.

The custom-theme section is user-authored, so it follows the project-name refusal policy: a malformed, unknown, missing or repeated token, a token without its `#`, a non-string base, an unknown field, a repeated id, a repeated name ignoring case, an invalid or built-in name, or more than 32 entries fails `load_from`, and every later preference write refuses with the original bytes intact instead of dropping themes. The section can only be repaired outside the app, so each refusal names the preferences file and asks the user to repair or remove its `custom_themes` section (`preferences::custom_themes_refusal`). Reading keeps at most one entry past the bound and skips the rest without parsing them as themes, so an oversized section costs no more memory than a full one and is refused with the bound. A well-formed base this build does not know, such as a built-in added by a newer release that still writes version 6, is not refused: the theme keeps its name and palette and its base becomes Braden or Midnight by the palette's lightness, as theme import does. Because a stored name equal to a built-in label is refused, a change that adds a built-in must also migrate custom themes already named like it; otherwise the new label would refuse those stores.

A theme document is the only file GitTurtle reads or writes outside application data and repositories, and the user names it in a native dialog every time. Export builds the document from the saved theme on the UI thread and writes it on the preference executor through `preferences::write_exported_document`: a temporary file beside the destination and a rename, so a refused or failing destination leaves no partial file and never truncates an existing one. Unlike application data it does not create the folder and keeps the platform's default permissions, because the user may share what they exported. Import reads the chosen path with the shared bounded reader (`read_store`, a regular file, no final-component symlink, at most `MAX_THEME_DOCUMENT_BYTES`) and parses and validates it on that same executor, so a large or hostile file cannot stall a frame; the UI thread only resolves the name against the saved themes, checks the 32-theme bound and submits `save_custom_themes`. `CustomTheme::from_document` owns every refusal message, and the reader's own refusals are translated where they name a condition the user can see in the picker. An imported theme is added and highlighted in the card, never applied: importing must not change the window's appearance. Cancelling either dialog is quiet, and a picker service failure carries the folder picker's Linux portal guidance without its repository-specific hint (`folder_picker::Picker`). A document is supplied bytes all the way into the card's text, so every fragment a message quotes from one — a key, a token value, the parser's own complaint, the unknown base — is clamped to `custom::MAX_MESSAGE_FRAGMENT_CHARS` where the message is built rather than where it is drawn; the import notice (`custom::import_notice`) additionally shares `custom::MAX_NOTICE_CHARS`, the card's measured two-line budget, among the strings it quotes, so a renamed import whose base was also replaced still reaches the clause naming the base that was used, and caps the quoted base at `custom::MAX_BASE_FRAGMENT_CHARS` because that unbreakable token wraps whole and has to share its line with the clause's fixed tail; and the export notice clamps the written path from the front so the file name survives. Nothing downstream, including the card's accessible name, then holds an unbounded string. Those clamps count characters, not pixels, so the card also draws an ellipsis where a message would run past its second line.

Store version 6 added the custom-theme section and the `ThemeSelection` form of `settings.theme`. Loading accepts versions 1 through 6 and never writes; stores before version 6 load with no custom themes and every other section unchanged, and the next explicit save of any section writes `"version": 6`. A version-6 store whose selection is a built-in differs from version 5 only in its version number and the added section. An older build refuses a version-6 store as unsupported, starts with defaults and keeps the file intact.

Persist normalized column widths/visibility, settings, recents and drafts outside repositories. Do not apply stale save replies over newer UI choices. Repository identity saves use the operation executor, not the app-preferences file.

Preference saves reread the current disk counterpart before atomically merging settings or recents; a stale UI snapshot must not replace both. Preserve read-only loading, supported-version migration and byte-safe recent paths. Invalid or unsupported stores produce a save error rather than being overwritten with defaults.

All application JSON stores share `preferences::read_store`: open one descriptor, reject nonregular files, and cap the bytes actually read even if the file grows. On macOS and Linux the open refuses a final-component symlink and uses nonblocking mode so a FIFO cannot stall startup or the persistence executor. Missing files retain each store's existing default behavior. Repository-session saves also validate the existing disk store: startup can show an empty view after corruption, but later navigation or shutdown must preserve the invalid original for recovery. The application-data parent belongs to the user; this does not isolate the app from another process with that user's filesystem permissions.

## Named Git profiles

`src/profiles.rs` provides the header menu and definition editor; its `store` module uses the existing preference executor and atomic writer. Saving, editing or deleting a definition changes app data only. Applying a profile uses `ProfilePlan` through the ordinary serialized write path, with the displayed worktree/config scope and stale configuration checks. A successful Git write records its app assignment separately; a storage failure must not replay Git application. Read effective author/signing configuration on the worker and show mismatch against the saved assignment. See [profile semantics and limits](../../../docs/profiles.md).

## Build diagnostics

`build.rs` embeds revision, clean/modified/unknown tree state, target, profile, compiler and build time; `build_info` presents that captured identity. Exact `--version`/`--build-info` requests exit before app-data and GPUI initialization. About and Copy bug diagnostics use the compiled values plus an explicit allowlist of display settings. Keep repository paths, credentials, environment dumps and runtime Git/process/network inspection out of this path.

Build metadata describes the executable's compilation, not the current checkout or packaging revision. A modified tree needs a source delta or compiled-input record alongside the executable identity before it can support a verification claim. Keep build-script rerun inputs aligned with compiled app/core/preview, dependency and embedded-asset changes; observing all `.git` activity would create unrelated rebuilds. The [Linux build identity notes](../../../docs/linux.md#build-from-source-on-ubuntu-2404) distinguish package metadata from executable identity. `build_info` unit tests validate the diagnostic allowlist; they do not establish package freshness.
